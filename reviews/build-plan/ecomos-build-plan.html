Build it the way the Meta gallery was built. One screen at a time, on a sample brand, in rounds of 10.

Each part of the business gets its own screen, its own folder and its own build sessions. A fictional US brand with generated data stands in for a client, so every screen can be built and judged now. The 560 capabilities, 235 workflows and 351 skills become the shelf each screen pulls from by id. The agent layer comes after the screens, because the screens show which buttons founders actually press.

From one long session holding everything to many short sessions holding one screen.

The sample brand

Tallgrass Goods, fictional.

A US direct-to-consumer kitchen and home goods brand: cast iron, linen, wooden boards, about 40 SKUs, average order around $85, Shopify, a 3PL in Ohio shipping UPS and USPS, paid social first, email second, Amazon as a secondary channel, no subscriptions. Every page says it is fictional.

Its facts live in one file, app/data/sample-brand/brand.json. A generator turns that file into 13 months of orders, customers, sessions, ad rows at ad level, email flows, tickets, reviews, products with costs, inventory, speed runs and marketplace listings, from a fixed seed, shaped like each connector's real export.

Why a normal brand first

Subscription brands need different numbers: payback period, churn, cohort revenue curves. They come later as a second sample brand with its own generator profile, not as a fork of the screens. The screens are built for the general case and gain subscription tiles when that brand exists.

Why generated data is honest

It is deterministic, labelled, and shaped like Shopify, GA4, Meta, Klaviyo and Gorgias exports. When a real brand connects, the same tables fill from read-only connectors and nothing in a screen changes.

A screen owns

Its page, its script, its API endpoints under its own path, its fixtures. It never imports another screen's code.

Contracts own

Every metric formula, every shared table, every kit component, every hand-off between screens. Changed in their own short session, committed first.

When two screens need the same thing

It becomes a table in the data layer. The producing screen writes it, the consuming screen reads it, the hand-off is listed in contracts/events.md. No screen calls another.

The round

Skeleton first, then 10 candidates, you pick, one feature per commit.

Round 0Shell in the kit, api.py, 3 tiles, 2 insights, 1 chart from the sample brand. Commit.
Ask for 10"Give me 10 candidates." The session pulls from 3 sources and ranks.
Source 1: room specFEATURES.md, seeded with the questions, metrics, insights, visuals and data this screen was specified with.
Source 2: the shelfThe catalogue for this screen's agent, its workflows and skills, by id.
Source 3: one web passWhat the common tools show today, so we know table stakes from new.
You pickRanked by revenue impact, usefulness to a founder deciding alone, buildable now on dummy data.
Build oneOne feature, one commit, FEATURES.md updated in the same commit. /clear. Next.
Publish the roundThe screen goes out as a page, like the gallery and the speed plan. Look at it on a phone.
A feature that needs data we do not have is parked with the connector named, not faked into the screen. Research sources like Reddit or Amazon reviews get a fixture file and a connector interface with the live call left as a named TODO.
Running it in Claude Code

One session per screen. Short by design.

Starting a session

Open Claude Code in the repo and name the folder and the round in the first line. The session reads app/CLAUDE.md, app/contracts/ and the folder. Nothing else.

Work in app/screens/07-landing-pages-cro.
Round 1. Give me 10 candidates.
Work in app/screens/07-landing-pages-cro.
Build feature 1.3 from FEATURES.md. One commit.

Which model for what

  • Fable: round 0 of the kit and server, contract changes, ranking the 10 candidates, and a short review of a screen's round before it is published.
  • Opus: building a picked feature.
  • Sonnet: a small feature, a fixture, a generator table.

Fable where judgement changes the outcome. Opus and Sonnet where the spec is already exact.

Parallel sessions

Screens in different phases can run at the same time in separate sessions and separate worktrees, because they share only contracts and data. Two sessions never edit contracts/ at once. A contract change is its own short session, committed first, then the screen sessions pick it up.

Token rules

  • Reference files with @path, never paste them.
  • /clear between features. The conversation is not the memory.
  • Ask for 10, pick, build one at a time. Never "improve the screen".
  • Commit after every feature so a lost session costs one feature.
  • Compaction should be rare because sessions are short.
Where agents and connectors come in

The screens are built as if the data and the agents were there. Two things fill them later.

Connectors

Read-only adapters in app/connectors/, each with a mock mode that returns the generated tables: Shopify, GA4, Meta Ads, Google Ads, Klaviyo, Gorgias, Search Console, Amazon Seller, review sites and Reddit for research, the speed lab. The generator's tables are shaped like each connector's export, so mock to live is a config change per brand.

Agents

Every action button already names its capability from the catalogue and shows its autonomy. Today the button logs the decision. When the agent layer is built, the same button dispatches the workflow. The screens tell us which agents to build first: the buttons founders press most.

What we do not do

Guardrails for this phase.

  • No agent execution yet. Buttons log decisions. The catalogue stays the spec.
  • No real brand data in the app. Gehna stays in the gallery until a connector migration is decided.
  • No India-specific defaults. Market fields exist in the schema and read null.
  • No feature without a formula, a rule or a capability id behind it.
  • No paid calls, no credentials in code, no writes to any external system.
