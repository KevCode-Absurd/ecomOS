## 2. Principles

### 2.1 Mindset and threat landscape (largely background; lightly card-covered)

1. **A vulnerability is the latent bug; an exploit is the working code that weaponizes it.** Triage and respond to these differently: a confirmed exploit against a live customer-facing surface is urgent, a latent vulnerability without a working exploit is scheduled work plus compensating controls (server-side checks, logging, rate limiting) while it waits for a real fix. [ca2a29d23a51]
2. **Never trust the client, because you do not control it.** A user's browser JavaScript runs on their machine; they can modify it, and they can send any HTTP request a normal browser UI would never generate (the source demonstrates this with a raw `curl` request to a server that has no button for that request). Any security decision that depends on "the UI doesn't have a way to do that" is not a real control. [91d7cee32897] [70ef0a4ed245]
3. **Map your attack surface by target, not just by feature.** The source's four-way split: the browser (isolation between tabs/origins), the server (must assume any request can arrive, however it was made), the client app / page JavaScript (can a crafted URL or embedded third-party script make it run code it wasn't meant to run — the seed of XSS), and the user themselves (social engineering, credential handling, tracking exposure). [91d7cee32897]
4. **Underground cybercrime is segmented by specialization** (background, not e-commerce-specific, no matching card, presented by the source as classroom discussion, not a cited study): distinct actors specialize in finding vulnerabilities, weaponizing them into exploits, buying/using compromised machines (botnets), monetizing compromised machines (DDoS-for-hire, ransomware, cryptomining, spam relay, keylogging/credit-card theft, webcam blackmail), and, for stolen card data specifically, separate specialists handle theft, physical counterfeit-card production, and cash-out (ATM withdrawal or in-store use). Ransomware's viability is attributed by the instructor specifically to cryptocurrency enabling anonymous direct payment (an opinion/framing, not a cited stat). DDoS-for-ransom (flood a site, demand payment to stop) is called out as "surprisingly common." None of this section has a matching card in this source's card set — treat it as scene-setting context for why a store is targeted, not actionable guidance.
5. **Two-factor authentication is the one named mitigation for social engineering** in this section: even if a credential is given away over the phone (the source recounts a real Def Con demonstration of how easily this works), a second factor stops that credential alone from being enough. No card matches this specific point in this source; it is standard-enough guidance to still record.

### 2.2 Supply chain and dependency risk

6. **Treat every dependency as code you are shipping, because full manual audit of a modern dependency tree is not realistic.** A single popular front-end package pulls in code from roughly a thousand contributors (the source's `npm install react` example); you cannot read all of it, and even careful review will still miss non-malicious bugs the original authors did not intend. Manage the risk instead of pretending you can eliminate it: lock dependency versions, review new *direct* dependencies before adding them, prefer well-maintained packages, and monitor lockfiles for unexpected changes. [f5ed3504c3e1]
7. **Watch for typosquatting on package names.** Worked example the source gives directly: a researcher registered package names one letter off from popular ones on public registries; the malicious code did nothing but silently ping the researcher's server on install/run, so almost no one noticed anything wrong (it worked exactly like the real package otherwise). Reported result: about 45,000 installs across roughly 17,000 different domains, including some `.mil` (US military) domains — meaning the code ran in production on government infrastructure. Registries have since added *some* defense (the source says npm began rejecting new package names that are near-permutations of a very popular existing name), but the source itself notes "there are still ways around that" — do not treat registry-side typosquat detection as a solved problem. [f5ed3504c3e1]
8. **Installing a package can already mean running arbitrary code on that machine** (post-install scripts execute automatically), so build inside a disposable/isolated environment, not a long-lived production host, and promote only the built artifact to production rather than a server that itself ran `npm install`. [6ada3852334a]
9. **Classify open-source/extension supply-chain risk into three buckets:** accidental maintainer mistakes, unmaintained/under-maintained packages, and deliberate malice (a rogue maintainer or a compromised maintainer account). Reduce dependency count and tree depth where practical (each transitive package is an implicit trust decision), vet third-party storefront scripts and payment/analytics widgets by who maintains them and whether they're still active, and be cautious of browser extensions on admin/back-office machines — popular extensions are sometimes sold to new owners who add malware or tracking, because extensions are otherwise hard to monetize. [58d9f7b5cc9d]

### 2.3 DNS

10. **Map the full DNS resolution chain to see every point a domain can be hijacked:** browser -> recursive resolver -> root nameserver -> TLD nameserver (e.g. `.com`) -> your domain's authoritative nameserver -> IP address returned back up the chain. Classic DNS queries are plain text (UDP-based), so any on-path device between the client and the resolver can intercept and answer first with a forged IP. [2117b632489b] [cc819036c4e0]
11. **Enumerate every hijack point, not just "DNS could be wrong":** malware editing a customer's or an employee's local hosts file; a compromised recursive resolver (frequently the ISP-supplied one); a compromised router; a directly compromised authoritative nameserver; and — the one that maps most directly onto merchant risk — a compromised DNS-provider/registrar account, since credential/account-takeover there lets an attacker edit records directly. Mitigate the parts you own: lock the registrar account with a strong, unique credential and MFA, and restrict who can edit DNS records. [2117b632489b]
12. **A DNS hijack can defeat the padlock, not just redirect traffic.** Domain-validated (DV) certificate authorities (the source's example: Let's Encrypt, "free to anyone who can prove control of a domain") validate control by checking the domain's current DNS/HTTP answer at issuance time. If an attacker has already hijacked the domain's DNS, the CA's own validation check gets redirected to the attacker too — so the attacker can pass domain-control validation and receive a real, browser-trusted certificate for the victim's domain. HTTPS/TLS gives integrity and authenticity for *a* connection, but cannot tell the browser the *domain* itself was never subverted upstream of issuance. [2117b632489b] [4d85411c726f] — Card [302263a7609a] adds the standard mitigation for exactly this gap: CAA DNS records constrain which certificate authorities are allowed to issue for your domain at all, closing part of this hole; this defense is not discussed by the lecture itself but directly answers the gap it describes.
13. **DNS queries are visible in plaintext to whoever resolves them**, and resolver operators (the source cites ISPs) have reportedly sold browsing-lookup history compiled from DNS logs. Partial mitigation: switch to a resolver with a stated no-sale privacy policy (source's example: Cloudflare's `1.1.1.1`) — but this only shifts trust, since the query is still visible in transit unless combined with DNS-over-HTTPS (DoH), which encrypts the query itself end to end. At the time of recording, Firefox defaulted to DoH and other browsers were only testing it, and OS-level (not just browser-level) DoH was not yet supported on macOS/Windows. `[web check: current DoH default/support across Chrome, Firefox, Safari, and OS-level support — this was current only as of a ~2019 recording]` [cc819036c4e0]
14. **ISPs themselves sometimes hijack DNS for non-attack reasons** (named examples: T-Mobile, Comcast) — intercepting a genuine NXDOMAIN (no-such-domain) answer and substituting a branded "search" landing page for ad revenue instead of a plain browser error page. This has misfired on real, existing HTTP (not HTTPS) sites. This behaves identically to a malicious hijack from the visitor's point of view and is a real-world argument for site-wide HTTPS: an ISP (or anyone else) intercepting an HTTP domain cannot produce a valid certificate to intercept an HTTPS one the same way. No direct card citation for the ISP-specific example; folds into the DNS-hijack cards above.

### 2.4 HTTP fundamentals

15. **HTTP request/response structure**: a request is a method (GET, POST, PUT, DELETE, etc.), a path, and a protocol version, followed by headers; a response is a protocol version, a status code and message, then headers, then body. HTTP/1.1 (dominant for roughly 15-20 years) is plain text and human-readable; HTTP/2 and HTTP/3 (introduced in quick succession after) are binary and not directly typeable. Headers are extensible because unrecognized keys are simply ignored, letting new features (caching, range requests, conditional requests) get added without a full protocol renegotiation. HTTP is stateless by design: two consecutive requests have no inherent relationship — anything that looks like persistent state (staying logged in) is layered on top via cookies, not the base protocol. [e3b4454386cb] [2705342004427]
16. **Use GET only for fetching a resource; use POST/PUT/DELETE for anything that changes state.** This is presented as a general safety principle, not merely a style preference — GET requests should be safe (no side effects) because browsers, proxies, prefetchers and third-party pages can all trigger a GET without the user's explicit intent (see the CSRF section below for why this matters concretely). [501cf413306c]
17. **URL structure and the injection root-cause**: scheme, host, port, path (not necessarily a literal file on modern dynamic servers), query string (`?key=value&key=value`, with a literal `&` inside a key/value requiring escaping), and fragment (`#`, scrolls to an in-page anchor; the source notes a then-forthcoming spec for text-based, Control-F-style fragment matching — `[web check: current browser support for text-fragment URLs]`). The source calls out explicitly: "one of the core problems of web security is distinguishing between what is part of the command you're issuing and what is user input" — the general data-vs-code confusion that recurs in XSS, SQL injection, and command injection alike. [b705e189b1eb]
18. **Status codes are a machine-readable retry/cache signal, not just a message.** 200 = success; 206 = partial content for a range request (e.g. seeking into a video by byte offset; if the server doesn't understand the `Range` header it falls back to a full 200, so clients must handle both). 301 = permanent redirect (browser caches the destination and stops re-asking — breaks anything meant to vary per visit, e.g. a "random page" link); 302 = temporary (re-asked every time). 304 = "not modified," returned to a conditional request (an `If-Modified-Since`-style header or version token) so the server can skip resending an unchanged body. 4xx = the client's fault (do not blindly retry unchanged — e.g. omitting the required `Host` header produces a 400); 5xx = the server's fault (worth retrying later, since the failure may be transient). 502/503/504 specifically describe failures between a reverse proxy and its backend servers (bad gateway / overloaded-or-down / timed out). [b4d32aeac67f] [8dafbe3112f2]
19. **`Host` header is required by virtually every server** for name-based virtual hosting (many domains can share one IP); omitting it typically produces a 400. **`User-Agent`** self-identifies the client (search crawlers self-identify, e.g. "Googlebot"); it is useful for traffic analytics and can be used for a coarse block of an obviously abusive, named scraper tool, but the client fully controls this header, so **treat it only as a weak signal, never as an access control** — anything relying on it can be bypassed by simply changing the header. [c86c31eeee98]
20. **`Referer`** (misspelled in the actual HTTP spec, kept forever for backward compatibility) shows the page a visitor arrived from and is useful for attribution analytics — but it is client-supplied, can be absent (privacy settings, referrer-policy opt-outs by the linking page) or spoofed, and additionally is unreliable for access control specifically because a cached response can be served from the browser's local cache without ever hitting your server again, so a Referer check on that path never even runs; there is also no way to stop another site from linking to you in a way that omits it. Do not use Referer as an access-control mechanism. [be4fc9dfbd67] [332f8d82f1e1]
21. **Caching headers and content negotiation**: `Cache-Control`/no-cache directives prevent sensitive or personalized responses from being cached; `Expires` sets a cache lifetime; `Vary` tells a cache which additional request headers must match for a cached response to be reused (worked example: a page cached for a Spanish-language request must not be served to a different visitor's Arabic-language request — `Vary: Accept-Language` fixes this) — apply the same reasoning to any dimension that changes the response, including logged-in state. `Accept`/`Accept-Language`/`Accept-Encoding` let a client negotiate format, language and compression. [f1e9ae8b0269] [7215ab0eb25a]
22. **The protocol stack is layered, and TLS is explicitly optional in it**: IP (addressing) -> TCP (reliable, ordered delivery) -> TLS (encryption — optional) -> HTTP (the actual data). Plain HTTP simply skips the TLS layer. A single page load triggers many round trips (the HTML, then every discovered sub-resource); this is a performance note, not itself a security control.

### 2.5 Cookies and sessions

23. **Mechanism**: server sends `Set-Cookie: name=value`; the browser stores it and automatically re-attaches `Cookie: name=value` on every later request to that site, with no page JavaScript required. This is what lets a stateless protocol support "stay logged in." A "session" is server-side state tied to a visitor across requests via this mechanism — named use cases: staying logged in, a shopping cart persisting for an anonymous/logged-out visitor `[applying source's general session concept to e-commerce cart persistence — the source's own examples are login and a generic preference cookie, not a store cart, but the mechanism is identical]`, and (the source's explicitly "nefarious" example) cross-site ad tracking, where the same cookie sent to an ad network embedded on many sites lets that network correlate one browser across all of them. [2705342004427] [4f8916cd06ba]
24. **NEVER trust an identity or authorization value that lives directly, unsigned, in a client-editable cookie.** Demonstrated live, not just asserted: an intentionally naive login system stored `username=alice` as a bare cookie with no signature and no server-side lookup; opening browser dev tools and editing the cookie's value to `username=bob` logged the attacker in as Bob with zero credential check, because the server trusted whatever the client claimed. The source's own words: "you'd be surprised how often people store important stuff like this in cookies." This generalizes to any claim (`role=admin`, `is_logged_in=true`, a user id) placed unsigned in a cookie. [0d3a15b17b43]
25. **Signing detects tampering but does not hide the value, and — critically — cannot be revoked.** A signature scheme (generator -> public/secret key pair; signer: secret key + value -> tag; verifier: public key + value + tag -> accept/reject) lets a server hand back `username=alice` plus a tag and later confirm the value was not edited; the plaintext value is still fully readable by the client, only *tampering* is caught. THE FLAW, demonstrated live as a deliberate lesson: if malware steals a validly-signed cookie, clicking "log out" (which just clears the browser's own copy) and even changing the password does **not** invalidate the stolen copy — a signature that is valid is valid forever, and the server has no record to delete for just that one credential (rotating the whole signing key would break every other user's session too). [922fb8a0700d] [ab2d784d0289]
26. **The correct session pattern is a server-side, revocable session table, not a self-contained signed token.** On login, generate a random, unguessable session id and store `session_id -> user data` (can hold an arbitrary object, not just the username) server-side; give the client only the opaque id. On each request, look the id up server-side to resolve identity — a missing/unrecognized id is treated as logged out. On logout, delete that one row: the stolen cookie's value now matches nothing and is dead immediately, without touching any other user's session. This is also what makes a "manage your active sessions, log out of other devices" account page possible (each row is independently deletable). Explicit caveat volunteered by the source: this defends against remote credential replay, not against malware with *persistent, live* access to the victim's machine — that is out of scope for any cookie-design fix. [aec0da259178]
27. **Session ids must come from a large cryptographically secure random space, never a sequential counter or another low-entropy scheme.** Demonstrated as a live failure: session ids issued as 0, 1, 2… let one logged-in user simply try nearby small integers and land in another user's session. Fix demonstrated: Node's `crypto.randomBytes(16)` (roughly 128 bits of entropy) converted to a string for use as a cookie value; collision at that size is not a realistic concern. Attempted alternative fixes tried and rejected live in the demo (binding to client IP, IP + User-Agent) fail because IPs are shared (a whole household behind one router looks identical) and change (mobile devices roam between cell towers), and combining with User-Agent still collides for two similar devices in one household. [6b4c9ca74bf3]
28. **Signing does have a legitimate use — just not sessions**: a value the client may see and even use, but must not be able to *edit*, and where the server never needs to revoke one specific instance of it. The source's example: a `discount=20` promo cookie, signed so a customer can't rewrite it to `discount=100`. Caveat raised and accepted live: an unencrypted signed cookie can still be *copied* wholesale to a different user/browser to duplicate the promo; binding the username into the signed value was floated as a partial mitigation, not fully resolved in this transcript. [ab2d784d0289]
29. **Cookie attribute reference, one by one, as the source demonstrates and evaluates each:**
   - **Expires**: sets an absolute lifetime. Without it, a cookie is nominally a "session cookie" meant to vanish at browser close, but modern session-restoration features often preserve it anyway — do not rely on browser-close to clear a cookie; set an explicit expiry if you need real expiry. [c9ef39d5290c]
   - **No delete API exists** — clear a cookie by re-sending the same name with any value and an expiry in the past (e.g. 1970-01-01); when clearing a cookie that was set with other attributes (Path, HttpOnly, SameSite, Domain), the clearing call must repeat those same attribute values or the browser treats it as a different cookie and the original survives. [8b10f43349b6]
   - **Path** ("this cookie only goes to requests under this URL prefix") is **demonstrated live to be broken as an isolation mechanism**: a cookie path-scoped to one URL prefix on a host is still fully readable by a same-origin page under a *different* path, by embedding the target path in a hidden iframe and reading `iframe.contentDocument.cookie` — because the real boundary is the Same-Origin Policy (protocol+host+port), not Path, and both pages share an origin. Guidance: never use Path to isolate two applications on one origin (use separate subdomains — different origins — instead); since Path gives no real isolation, just set `Path=/` on every cookie explicitly so you are not fooled into thinking you have protection you don't. [d721b7f8d72e] [4388ab8bc2f2] [a88d4d33040c]
   - **Domain** ("cookies can only be accessed by equal or more specific domains," not the intuitive-sounding reverse): a cookie set broadly (e.g. `Domain=example.com`) is visible to every subdomain; a cookie set narrowly on one subdomain (no Domain attribute) is invisible to sibling subdomains and to the bare parent domain. Real pattern named: put a login/auth flow on its own dedicated subdomain specifically so unrelated apps on sibling subdomains of the same parent cannot read that cookie. Only widen `Domain` when cross-host sharing is a genuine, deliberate requirement. [cbe19c92fd05]
   - **Secure**: cookie is withheld on any unencrypted (HTTP) connection. Framed as a fallback for mixed HTTP/HTTPS legacy stacks, not the real fix — the real fix is serving the *entire* site over HTTPS so the question never arises (see session hijacking below). [031a3c4a2437]
   - **HttpOnly**: makes the cookie invisible to `document.cookie`/page JavaScript while still sent normally in request headers — direct defense against script-based cookie exfiltration (see 2.6). Do not apply it to a cookie the page's own JS is intentionally designed to read (e.g. a UI preference). [f4015dad3b23]
   - **SameSite**: see 2.6/CSRF below — this is the cookie attribute that answers CSRF specifically, not a general-purpose isolation setting.
30. **Reading/writing cookies via `document.cookie` is a famously bad API**, preserved only for backward compatibility: assigning to it *appends* a new cookie rather than overwriting one of the same name, and reading it returns every cookie as one semicolon-delimited string with no built-in per-name lookup. If client-side cookie manipulation is genuinely needed, use a library rather than hand-rolling parsing. [c9ef39d5290c]
31. **Ambient authority**: access control based on a global, persistent property automatically attached to every request (the cookie header), rather than the user re-proving identity on every single action. This is *why* staying logged in while browsing works at all, and it is also exactly the property CSRF abuses (2.6). Cookies are, per the source, by far the dominant ambient-authority mechanism on the web; two more obscure alternatives are named — IP-based access control (workable only in narrow contexts, e.g. a university library restricting access by on-campus IP range; breaks down for shared household IPs and roaming mobile IPs) and the browser's built-in HTTP Basic Authentication popup (effectively abandoned for its poor, uncustomizable UI) — neither is presented as viable for a general storefront. [e734ff1cfc33] [1cf7e74aa70a]
32. **The ambient-authority principle applies just as much to non-human callers as to shoppers.** Any long-lived automation credential (an API key, an OAuth token, a service-account credential used for a price sync, inventory feed, or order-processing agent) behaves exactly like a stateless signed cookie if it cannot be individually revoked: store such credentials server-side in a revocable record, scope each one narrowly to the specific brand and task it serves rather than full-account access, generate them from a secure random source (not a predictable scheme), and log which credential performed which action so a compromise's blast radius is knowable. `[applying the source's cookie/session principle to agent and API-credential design — the source itself discusses cookies, not automation, so this generalization is this playbook's own extension, though the underlying mechanism (ambient, unrevocable authority) is identical]` A document or tool output an autonomous agent reads is untrusted data, never an instruction granting it further authority — that authorization must come only from the store owner and the credential's configured scope. [53a7573439db]

### 2.6 Session hijacking and script-based cookie theft

33. **Session hijacking**: if a session cookie ever travels over an unencrypted connection, anyone observing that traffic (same coffee-shop Wi-Fi, same local network segment) can copy and replay it, and the server has no way to distinguish the replay from the legitimate holder. Named historical case: Firesheep (2010), a Firefox extension that put a network adapter into promiscuous/monitor mode and let the user passively harvest other people's unencrypted session cookies (e.g. to Facebook, unencrypted at the time) from a shared network, released deliberately to pressure sites into full-site HTTPS. Directly relevant pattern the source calls out as insufficient: encrypting only the login POST (to protect the password) while every later authenticated page reverts to plain HTTP — the session cookie is just as valuable as the password once a visitor is logged in, and it is exactly what is left exposed by that pattern. The fix: serve the *entire* site over HTTPS, not only checkout/payment pages; the `Secure` cookie attribute is a fallback for a still-mixed legacy stack, not a substitute. [031a3c4a2437] [047c9059541]
34. **XSS-based cookie theft, mechanics only (full XSS mechanics are promised "next time" and not reached in this part):** if an attacker gets their own script to execute inside a victim page, a simple exfiltration technique is dynamically creating an `<img>` whose `src` points at an attacker URL with the cookie value appended as a query parameter; the browser fires the GET as if fetching an image, the "image" need never actually resolve, and the attacker's server logs the leaked value from the request itself. This is a general pattern for exfiltrating anything JS-readable, not cookie-specific — hence the standing recommendation to mark session cookies `HttpOnly` so this exact technique cannot read them in the first place. [08daf97306073] [a1ee46e37a85 — caution: cite only for the general img-exfiltration mechanism; do not extend this card's login-button-width side-channel content to this part, since that specific inference technique is not covered in the text read for part 1]

## 3. Procedures

### 3.1 Worked demo: insecure login -> signed cookie -> revocable session (the source's own three-stage build)

This is the source's own live-coded progression (Node.js + Express), presented explicitly as "build it wrong, see why, fix it, see the next flaw, fix that." Reproduce the *reasoning*, not necessarily this exact stack, on any real login/session system.

1. **Stage 1 — naive and broken.** Parse the login POST body with a body-parser middleware (`req.body.username`, `req.body.password`) and cookies with a cookie-parser middleware (`req.cookies`). [9dafe13a37b6] Compare the submitted password against a stored value (a stand-in for a real user store) and, on match, set `res.cookie('username', <submitted username>)` — a bare, unsigned value. Read `req.cookies.username` on the home route to decide what to show. **Flaw** (2.5 #24): editing the cookie in dev tools to any other username logs the attacker in as that user with no check at all.
2. **Stage 2 — signed cookie.** Add a cookie-signing secret to the cookie-parser setup; set the cookie with `signed: true`; read only `req.signedCookies` (tamper-evident: a bad/missing signature simply omits the property, read as "logged out"). This stops cookie *editing* but introduces the unrevocable-token flaw (2.5 #25): a copied, still-validly-signed cookie keeps working after logout and even after a password change.
3. **Stage 3 — server-side session table (the fix the source lands on).** Replace the signed username cookie with: an in-memory (in a real system, persistent) `sessions` map from a random session id to user data; on login, generate the id with `crypto.randomBytes(16)`, store `sessions[id] = username`, and set only that opaque id as the cookie; on each request, look the id up in `sessions` to resolve identity (missing = logged out); on logout, `delete sessions[id]` so the browser's now-stale cookie value resolves to nothing. [aec0da259178] [6b4c9ca74bf3]
4. **Hardening pass — cookie attributes applied together** once the session-table design is in place: `Secure` (omit only for local plain-HTTP dev — not a production choice), `HttpOnly`, `SameSite=Lax` (or `Strict` for an especially sensitive flow — 3.2 below), an explicit `Path=/`, and a bounded `Max-Age` (source's number: roughly 30 days, in milliseconds: `30*24*60*60*1000`), refreshed by resending the same `Set-Cookie` with a new expiry on every return visit rather than issuing one very long-lived cookie up front. When clearing, repeat every one of these attributes on the clearing `Set-Cookie` call or the browser will not recognize it as the same cookie. [f4015dad3b23] [56b8e42ca03f]

### 3.2 Worked demo: CSRF attack and the SameSite fix

1. **Vulnerable baseline**: a `/transfer` POST endpoint on the demo bank app reads the logged-in user from the session cookie and moves funds between two hardcoded balances, with no per-request secret beyond the ambient session cookie.
2. **Attack build (GET variant, described, not separately demoed on this endpoint)**: embed `<img src="https://target/transfer?amount=1000&to=attacker">` on any page; if the target endpoint is a GET and state-changing (a design flaw in itself — see 2.4 #16), the browser fires the request as if loading an image, the browser attaches the victim's cookies for that origin automatically, and the transfer executes; the attacker never needs to read the (non-image) response for the attack to succeed. [638455ba9453] [a1ee46e37a85]
3. **Attack build (POST variant, live-demoed against the /transfer endpoint after switching it to POST specifically to show POST alone is not a fix)**: build a hidden (`display:none`) auto-submitting HTML `<form>` with pre-filled `amount`/`to` fields whose `action` is the *absolute, cross-origin* target URL; embed it (via a second hidden iframe holding that form) inside an otherwise innocuous decoy page; add a script calling `.submit()` on page load. If the victim is currently logged into the target site in the same browser, simply visiting the decoy page silently completes the forged transfer with zero visible UI change — confirmed live in the demo. This works specifically because plain HTML form submission is allowed to cross-site targets by browser design, called out explicitly as a legacy exception to the Same-Origin Policy kept only for backward compatibility. [08daf97306073] [9a7ac826028b]
4. **Escalation note**: the same pattern against a privileged/admin session is far more damaging — the source's example is a forged request that creates a new admin account on a WordPress-style admin session, or in some configurations achieves server-side command execution as the server user. [08daf97306073]
5. **Fix applied and verified live**: set `SameSite=Lax` on the session cookie (withholds it on cross-site sub-resource requests — embedded images, iframes, form posts triggered by a foreign page — while still sending it on ordinary top-level navigation, e.g. clicking a link that takes the whole browser tab to the site). Re-running the same forged-form attack after this change correctly failed to transfer funds. [f4015dad3b23] [c2bad816cf64]
6. **Debugging pitfall surfaced live and worth repeating as a procedure step**: the fix did **not** initially appear to work when both the bank and the "attacker" page were served from `localhost` differing only by port — cookie scoping (2.5 #29, Domain) checks only the hostname, and `localhost` was identical for both, so the browser did not classify the request as cross-site. The attack was only correctly blocked once the attacker page was given a distinct hostname. **Practical implication for any team testing this fix**: test SameSite/CSRF defenses with genuinely different hostnames, not same-host-different-port setups, or you can walk away believing a fix works when it has not actually been exercised. [f4015dad3b23] [ae9902b8b7a8]
7. **Explicit residual gap, stated by the source itself, not resolved in this part**: "SameSite... is actually not a complete solution." The source frames a further/complementary defense (implicitly, anti-CSRF tokens) as coming later in the material — not covered in lines 1-1303 of this text and therefore not in this part. [9a7ac826028b] [ae9902b8b7a8]

### 3.3 Diagnosing the Same-Origin Policy live, origin by origin (source's own check-list of demos)

The source runs through these checks live to build intuition for what SOP does and does not restrict; reproduce the same checks against your own storefront's third-party embeds/CDNs/widgets to know which of your own cross-origin relationships are protected and which are not.

1. Define an origin as the triple **(scheme, hostname, port)**; all three must match for two browsing contexts to be same-origin. Confirmed by direct comparison: same scheme+host, different path = same origin; `www.x.com` vs `x.com` = different (host differs); `http` vs `https` on the same host = different (scheme differs); default port 80 vs. an explicit non-80 port = different.
2. **Same-origin iframe** (two pages on the same host/scheme/port): embedding is allowed, and the embedding page can freely read/modify the framed page's DOM and cookies via `iframe.contentDocument` — this is exactly how the Path-scoping "flaw" in 2.5 was demonstrated.
3. **Cross-origin iframe**: embedding is still allowed, but `iframe.contentDocument` returns `null` — DOM/cookie access is blocked. Navigating the cross-origin frame to a new URL from the parent's script, however, *is* still allowed — an inconsistency the source itself calls out as surprising.
4. **Cross-origin `fetch()`**: blocked by default with a browser-level CORS error, specifically because the request would otherwise carry the target origin's cookies and hand back personal, cookie-gated response data to a different, uncooperating origin's script (the source's stakes example: without this block, any page could silently `fetch()` a victim's logged-in Gmail inbox using the victim's own ambient cookies). A plain server-side `curl` to the same URL succeeds and returns only public content, because it carries no browser cookies — the SOP restriction is specific to browser-mediated, cookie-carrying, script-initiated requests, not to the resource being unreachable in general. CORS is named as the deliberate, opt-in mechanism to relax this when a site wants to expose an API to other origins' scripts on purpose; its mechanics are not covered in this part. [55a5c844c21a]
5. **What SOP allows across origins regardless**: plain linking, `<iframe>` embedding, embedding images/scripts/stylesheets (this is how shared-CDN caching works, though the source notes it is "less useful these days" given how much custom/unique code modern site builds ship), and — the explicit, named legacy exception — HTML form submission. [55a5c844c21a]

## 5. Diagnostics and checks

- **Cookie/session audit**: for every cookie your storefront sets, check whether it carries an identity or authorization claim in plaintext (fail: rewrite to a random server-side session id — 2.5 #24/#26), whether it is signed where signing is the *wrong* tool (fail if it's a session — 2.5 #25/#26), and whether it sets `Secure`, `HttpOnly`, `SameSite`, an explicit `Path=/`, and a bounded expiry (fail any missing attribute — 2.5 #29). [f4015dad3b23]
- **CSRF exposure audit**: list every endpoint that changes state (per this part's terms, "state-changing" — a store's own equivalents would include things like account or address changes, though the source's only worked example is a funds transfer). For each: is it reachable via GET (fail — 2.4 #16, 3.2 #2)? Does it authorize solely on the ambient session cookie with no additional per-request check (fail if so, given SameSite alone is stated as incomplete — 3.2 #7)? Is the session cookie's `SameSite` value actually tested against a *different-hostname* attacker origin, not just a different port on the same host (the source's own debugging pitfall — 3.2 #6)? [08daf97306073] [9a7ac826028b]
- **Path-scoping check**: if any cookie relies on `Path` to separate two applications/teams on the same host, treat that as already broken (per the live demo in 2.5 #29) — the fix is separate subdomains (separate origins), not a narrower path.
- **DNS/registrar check**: confirm who can edit your domain's DNS records and whether that account has MFA; confirm whether CAA records are set to constrain which CAs may issue for your domain (closes the gap in 2.3 #12). [2117b632489b] [302263a7609a]
- **Referer/User-Agent reliance check**: search your own access-control or bot-blocking logic for any decision keyed on `Referer` or `User-Agent` alone; both are client-controlled and, per this source, should be treated as analytics signals only, never as the sole gate. [c86c31eeee98] [332f8d82f1e1]
- **HTTPS coverage check**: confirm the entire site is served over HTTPS, not only the login form or checkout pages — the source's own historical failure case (encrypt only the password, leave the session cookie traveling in the clear afterward) is the exact pattern Firesheep exploited. [031a3c4a2437] [047c9059541]

## 7. Examples and case results

All of the following are the source's own illustrative examples, not controlled studies or benchmarks — treat every number as historical color, not a current baseline.

- **Insecure-cookie demo**: editing `username=alice` to `username=bob` in dev tools logged the attacker in as Bob instantly, no password required. [0d3a15b17b43]
- **Sequential session-id demo**: session ids issued as 0, 1, 2… let a second logged-in user (given id 2) guess that a lower id (e.g. 0 or 1) might belong to an earlier user and simply try it. [6b4c9ca74bf3]
- **Path-isolation demo**: a cookie scoped to `path=/class/cs106a` on a shared host was still fully readable from a same-origin page under `/class/cs253`, via a hidden iframe and `contentDocument.cookie`. [d721b7f8d72e]
- **CSRF demo**: a hidden, auto-submitting cross-origin form inside a decoy "cool cat site" silently transferred funds from a logged-in victim's demo-bank balance to the attacker's account, with zero visible page change; switching the endpoint from GET to POST alone did not stop it. [08daf97306073]
- **SameSite localhost pitfall**: the same CSRF fix appeared to fail in testing purely because the attacker page shared a hostname (`localhost`, different port) with the target; moving the attacker page to a distinct hostname made the fix work as expected. [f4015dad3b23]
- **npm typosquatting research incident**: ~45,000 code executions across ~17,000 domains, including some `.mil` domains, from packages registered with names one letter off from popular ones. [f5ed3504c3e1]
- **Firesheep (2010)**: a Firefox extension let anyone on a shared network passively harvest other users' unencrypted session cookies (e.g., to Facebook) and hijack their sessions with a UI click, released to pressure sites toward full-site HTTPS. No matching card in this source's set; recorded here as a named historical incident only.
- **WordPress admin-creation worm** (recounted, not demoed live): stored XSS in the WordPress database caused injected code to create a new, attacker-known admin account whenever a logged-in admin viewed the affected page; the attacker then mass-tried those known credentials across many WordPress installs. Described by the instructor as "pretty recent" relative to the recording. No direct card in this source's set for the WordPress-specific worm mechanics as told in this part (the source's card set covers the general MySpace/Samy stored-XSS worm pattern instead — see [0046b75dd217] — which is thematically the same lesson).
- **Local-storage quota-bypass anecdote** (personal, not e-commerce): a per-subdomain 5MB storage quota was defeated by generating unlimited free subdomains, each granted its own 5MB, to fill a victim's disk/RAM; fixed since in all major browsers except (at the time it was found) Firefox, which was already unaffected. No matching card; general web-platform history, not e-commerce-actionable.

## 8. Mistakes the source warns about

- Storing an identity/role claim directly and unsigned in a client-editable cookie. [0d3a15b17b43]
- Treating a signed cookie as sufficient for session management — signing detects tampering but cannot be revoked, so logout and "change my password" do not actually invalidate a stolen, still-validly-signed cookie. [aec0da259178] [ab2d784d0289]
- Using sequential or otherwise low-entropy session identifiers. [6b4c9ca74bf3]
- Relying on `Path` to isolate cookies between two applications sharing one host. [d721b7f8d72e] [4388ab8bc2f2] [a88d4d33040c]
- Assuming closing the browser clears a cookie with no explicit `Expires` — session-restoration features often preserve it anyway. [c9ef39d5290c]
- Encrypting only the login form/password submission and leaving the rest of an authenticated session on plain HTTP — the session cookie itself becomes the exposed asset. [031a3c4a2437] [047c9059541]
- Believing switching a state-changing endpoint from GET to POST alone stops CSRF — plain HTML form submission crosses origins by design. [08daf97306073] [9a7ac826028b]
- Testing a SameSite/CSRF fix using two ports on `localhost` instead of genuinely different hostnames, and concluding the fix works when the test never actually exercised cross-site behavior. [f4015dad3b23]
- Relying on `User-Agent` or `Referer` as an access-control mechanism rather than a weak analytics signal. [c86c31eeee98] [332f8d82f1e1] [be4fc9dfbd67]
- Assuming a `npm install`-style dependency tree has been, or even could be, fully manually audited. [f5ed3504c3e1] [58d9f7b5cc9d]
- Running package installation on a long-lived production host rather than a disposable build environment. [6ada3852334a]
