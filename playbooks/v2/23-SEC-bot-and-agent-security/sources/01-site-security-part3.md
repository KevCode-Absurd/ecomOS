## 1. What this source is for

This part teaches an operator or engineer how phishing, side-channel leakage, and code injection actually work mechanically (enough to defend against them, not to build them), and then teaches the transport-security layer that sits on top of HTTPS: HSTS, the certificate-authority trust model and its historical failures, and the mechanisms (pinning, CAA, Certificate Transparency) built to compensate. It closes by opening the topic of authentication (the three factors, and why biometrics must stay on-device). For a store's engineering/security operator, the direct payoff is: (a) how to test for and close command injection and SQL injection in any server-side code that builds shell commands or SQL from user input; (b) what HSTS and CAA actually do, their real deployment gotchas, and why certificate pinning is no longer recommended; (c) how to recognize phishing and UI-spoofing techniques your support team or fraud team may encounter reported by customers; and (d) a mental model for side-channel risk (a system can be "correctly" built and still leak data) to apply skepticism to any client-side feature that reads ambient signals (image sizes, timing, sensors) across origins.

## 2. Principles

1. **Untrusted input mixed with trusted code/commands is the root cause of all injection attacks**, whether the target interpreter is a shell (command injection), a SQL engine (SQL injection), or a browser DOM (XSS, covered elsewhere in this source). The fix is always the same shape: never build a command/query by string concatenation with attacker-controlled data; use an API that takes the trusted program/query and the untrusted values as separate, structurally-escaped parameters. Applies whenever any request-derived value (query string, form field, cookie, header) reaches a shell-exec call or a SQL string template. [d5c07946bb53] [f4b6df714ffd] [00899c6e9eb7] [45a137425080]
2. **A system can be functioning exactly as coded and still leak sensitive information through a side channel** (timing, layout, physical sensors) that nobody designed to be an information channel. This is a distinct class from an implementation bug: there is "nothing wrong with the lines of code," yet information escapes. Applies to any client-side feature that reads a shared, observable resource (render timing, screen brightness via ambient sensors, device motion, image layout) that varies with hidden per-user state (browsing history, login state, secret content). [c16f92a5d2c1] [ec15a57caac8] [09f369da8351]
3. **Positive security indicators do not reliably work.** A UI signal (the padlock icon) that appears only when something is safe, and is silent otherwise, depends on users noticing an ABSENCE — research shows most users do not. Any anti-phishing UI design that relies on "the user will notice when the good sign is missing" should be treated as unreliable by default, not merely imperfect. Condition: applies specifically to absence-based cues, not to affirmative, hard-to-miss warning interstitials (which the same source's cited research shows DO reduce click-through, see section 4). [b6d76d1c801a] [c16584de911d]
4. **Password managers and hardware security keys are origin-bound defenses that survive UI-level phishing deception**, because they check the actual origin/domain cryptographically or by exact match, not by what the page visually displays. This holds even when the visual UI is completely successfully spoofed (homograph domains, fake browser chrome, picture-in-picture attacks) — the user's eyes can be fooled, but the credential manager cannot. Recommend both as concrete, currently-effective mitigations for account-takeover-via-phishing, independent of UI hardening.
5. **Biometric authentication data must never leave the device it was captured on.** Biometric data is unlike a password or key: it cannot be reset or reissued once compromised. Modern, correctly-designed biometric auth (source's example: iPhone Touch ID/Face ID) uses the on-device biometric check only to unlock a local secure key store; the actual authentication to a remote server uses a resettable cryptographic key from that store, never the raw biometric. Any authentication feature design that would transmit raw biometric data to a server violates this principle. [a55298b2b401]
6. **The more of the three authentication factor categories (something you know, something you have, something you are) a system combines, the more confidently it verifies identity claims** — the basis for multi-factor authentication. Stated as a general principle at the start of the authentication unit; the source does not yet (in this part) qualify it with the caveats that make some factor combinations weaker than others (e.g., SMS-based "have" factors) — expect that nuance in part 4. [a55298b2b401]
7. **The Certificate Authority trust model is fundamentally "any CA can issue for any domain," which is deliberately open** (so any legitimate site can buy a cert from any CA it trusts) but also means a single compromised CA anywhere in the world can be used to impersonate ANY site to anyone positioned on the network path. This is presented as a structural property of the web PKI, not a bug to "fix" by restricting issuance geographically (see section 9 for why that specific fix fails). [380c74d6b66f]
8. **Detection-only security mechanisms (Certificate Transparency, CAA) still provide real value even without real-time prevention**, by making attacks and mistakes noisy/discoverable rather than silent and indefinite. This is explicitly weaker than a prevention mechanism (key pinning), but the source's own experience is that the prevention mechanism (pinning) was removed because its usability/lockout costs outweighed its stronger guarantee — illustrating a general trade-off principle: a weaker-but-usable control that ships and stays on is worth more in practice than a stronger control users/operators cannot reliably operate. [46771a8e61d2] [302263a7609a] [214a75be3710]
9. **Client behavior that a server operator relies on (which root CA a browser trusts, which chain it builds, what its URL bar displays) is not something the server can reliably predict or control**, because of the sheer diversity of clients, versions, platforms, and administrator policies. Any security mechanism a site adopts that depends on predicting exact client-side behavior (this source's example: key pinning's chain-building mismatch) is fragile for this reason and should be treated with suspicion. [214a75be3710]
10. **HSTS opt-in is a one-way ratchet once real users have cached it**: there is no way to instantly undo it for users who already cached a given `max-age`. This argues for starting with a low `max-age` and raising it gradually as confidence in the HTTPS deployment grows, rather than committing to a long value immediately. [982af2ed0756]
11. **Any browser feature or API that exposes ambient, cross-origin-observable state (timing, sensor readings, image dimensions, persistent flags) is a potential side channel or tracking vector**, even when it was never designed with that intent (visited-link styling, ambient light sensors, gyroscopes, and even HSTS's own persistent per-domain flag have all been demonstrated as exploitable in this way). Treat any new "innocuous" browser capability with this lens before assuming it is privacy-neutral. [3db5a465b9a7] [5e21182dfef5] [989b6ffaf61b]

## 3. Procedures

### 3.1 Basic SQL-injection diagnostic test
1. Find an input field or parameter that reaches a database query (login form, search box, filter parameter, etc.).
2. Submit a single or double quote character as the value.
3. If the application returns a database/syntax error where it normally would not (a literal quote should be harmless user data, not special syntax), treat this as a strong indicator the input is unsafely interpolated into a SQL query. [00899c6e9eb7]
4. This is stated as "the most common way to test if a site is vulnerable to SQL injection" — use it as a first-pass check on any input, not a full audit.

### 3.2 Constructing (for defensive verification only) a classic authentication-bypass SQL-injection payload, and what each part does
Documented here strictly so a defender can recognize this exact payload pattern in logs, WAF rules, or pentest reports — not as attack instructions to deploy against a system you do not own or have authorization to test.
1. Submit a username value ending in a quote, immediately followed by a SQL comment marker (two dashes, `--`), which neutralizes the trailing quote the application's own query template would otherwise add, restoring valid query syntax. [00899c6e9eb7]
2. To bypass a login predicate entirely, follow the comment marker with an always-true OR clause (e.g., an unconditional true predicate) so the WHERE clause matches every row regardless of the actual submitted username; if the underlying query-execution wrapper only returns a single row (as in the source's demo), this typically authenticates as whichever row is returned first, not a specific chosen account.
3. If the underlying database client library exposes an "execute multiple statements" API (the source's example: a generic `exec`-style call, as opposed to a safer single-row `get`-style call that refuses to run more than one statement), an attacker can chain a semicolon plus an entirely separate, destructive statement (e.g., an `UPDATE` to change another user's password, or a `DROP TABLE`) onto the injected input. **Defensive takeaway:** avoid using any multi-statement-capable query API to build queries from unsanitized/interpolated user input, even where you believe the input has already been "cleaned" for the primary query. [478efa2d244c]

### 3.3 Recognizing and testing for blind SQL injection (defensive)
1. If a suspected-vulnerable endpoint does not directly expose query results in its response (no visible error, no visible data change), check for BEHAVIORAL blind SQL injection first: inject a boolean sub-condition and see if it changes the page's observable behavior (e.g., causes a crash when zero vs. one-or-more rows are unexpectedly returned to code that assumed exactly one). A difference between "crashes" and "doesn't crash" for a true vs. false injected condition is a working "yes/no" oracle. [976966f18f9b] [ef4261b02222]
2. If there is no observable behavioral difference at all, check for TIME-based blind SQL injection: inject a conditional SQL expression that performs a deliberately slow operation (the source's example: constructing then uppercasing a large hex-encoded blob and searching within it, and comparing it, which the source's demo measured at roughly one-third of a second) only when the injected boolean condition is true, and effectively nothing when false. Measure response time; a consistent, reproducible delay on "true" versus near-instant on "false" confirms a working timing oracle.
3. To extract secret data (the source's demonstrated example: an existing user's password) via a timing oracle, iterate: for each character position, test each candidate character (e.g., testing a `SUBSTRING`/first-letter-equals-`X` predicate) and observe which single candidate produces the slow-path timing; that candidate is confirmed for that position; then move to the next position. The source notes this technique's effectiveness is entirely independent of the target value's own complexity — a "secure" password is extracted exactly as easily as a weak one, character by character. **Defensive takeaway:** this is why blind/time-based SQL injection is dangerous even when an application never displays query output — the absence of visible output is not a mitigation on its own. [976966f18f9b] [ef4261b02222]

### 3.4 Fixing command injection (the argument-array pattern)
1. Identify anywhere untrusted, request-derived data (URL parameter, form field, cookie, or any other client-supplied value) is combined via string concatenation into a value passed to a shell-execution call (source's example: Node's `child_process.execSync` given a single, interpolated command string).
2. Replace the single-string, concatenated call with an API that takes the program name and an ARRAY of discrete argument strings separately (source's example: Node's `spawnSync`, called as `spawnSync('cat', [userSuppliedFilename])`), and let that API handle escaping.
3. Verify the fix by submitting a value containing shell metacharacters (e.g., a value ending in `; ls` or similar): confirm the entire malicious-looking string is now treated as ONE literal argument (e.g., causing a "file not found" for the whole string) rather than executing a second command.
4. Note explicitly that this fix does NOT address a separate, independent vulnerability: if the underlying feature lets the user specify an arbitrary file PATH (e.g., a "view any file by name" endpoint), argument-array escaping alone does not prevent path traversal to unrelated files on the server; that requires separately restricting which paths/files the feature is allowed to serve. [d5c07946bb53] [f4b6df714ffd] [45a137425080]
5. Cross-language note (explicitly stated, not detailed by the source beyond Node): essentially every mainstream server-side language offers both an unsafe string-concatenation shell-execution pattern and a safer argument-array/list pattern; identify and use the safe pattern for your specific language and runtime. [needs source data: the source names only Node's `spawnSync`; it does not name the exact equivalent APIs in Python, Ruby, etc. — verify per-language before relying on a specific function name]

### 3.5 Testing whether a browser correctly protects against IDN homograph domains (conceptual, defensive; for your own security awareness/training, not for building lookalike domains)
1. Compare the byte-level content of a suspicious URL against the legitimate URL it resembles (a hex editor or byte-diff tool, as demonstrated live in the source, can reveal that visually identical characters diverge at the byte level starting where a lookalike Unicode character is substituted).
2. Note that a modern, correctly-behaving browser should render a suspicious mixed-script or fully-lookalike-script domain as punycode (an `xn--`-prefixed ASCII string) rather than the native characters, specifically when: the domain mixes characters from two different scripts where the non-Latin character looks like a Latin letter, OR the entire domain is one non-Latin script AND its TLD is not itself an internationalized TLD. [4f89f80a0b9a]
3. Do not rely on this browser behavior alone as your organization's sole anti-phishing control, since the source explicitly documents at least one real, then-current browser gap (Firefox failing to punycode-render an all-one-script lookalike domain) — treat browser-side punycode rendering as one layer, and origin-bound credential tooling (password managers, hardware keys) as the layer that keeps working even when the visual layer fails. [4f89f80a0b9a] [web check: current per-browser IDN homograph handling — this source's specifics are dated ~2018-2019]

### 3.6 Explaining "is this really PayPal" to a non-technical user, and its limits
1. Rule of thumb given: from the URL, find the first `/` after the scheme, then walk back to the two dot-separated labels immediately preceding it — that span is the real registrable domain.
2. Acknowledge explicitly (as the source does) that this rule is genuinely hard to teach non-technical people, because the important, trust-bearing part of the URL sits in the middle, between attacker-controlled segments on both sides (a long fake subdomain in front, an attacker-controlled path/query after). [8b968c78d019]
3. Do not assume the browser's own URL bar rendering will reliably help: the source demonstrates that narrowing the browser window (or an attacker simply padding a fake subdomain with enough characters) can push the true registrable domain off-screen entirely, defeating even browsers (Firefox) that otherwise gray out the fake subdomain portion. [8b968c78d019] [web check: current per-browser URL-bar truncation/graying behavior — dated to the source's recording]

### 3.7 HSTS opt-in and rollout
1. To opt a site into HSTS, serve an HTTP response header carrying (at minimum) a `max-age` directive. [05ffb117c836]
2. Start with a LOW `max-age` when first deploying HTTPS/HSTS, to limit exposure if something is misconfigured, then raise it incrementally as confidence grows — mature deployments typically use a long value (on the order of one to two years). [982af2ed0756] [web check: current recommended/maximum max-age values]
3. Decide on `includeSubDomains` deliberately: it extends the policy to every subdomain, which is good practice in general but will break the rollout entirely if even one or two vendor-operated subdomains do not yet support HTTPS — resolve those subdomains' HTTPS support FIRST, or defer `includeSubDomains` until they do. [982af2ed0756]
4. If you want a `www.example.com` landing page to set domain-wide HSTS (via `includeSubDomains`) despite no built-in HSTS mechanism supporting this directly, the source describes the real-world workaround of loading an invisible sub-resource from the bare registrable domain (`example.com`) and setting the HSTS header (with `includeSubDomains`) on THAT response. [needs brand data: whether your own storefront platform supports or requires this workaround — it is not a documented standard, just an observed practice]
5. Understand that this workaround protects returning visitors only; the very FIRST time any given browser contacts your domain, no HSTS record is yet cached, so that connection remains vulnerable to downgrade — see 3.8 for the preload-list option that closes this specific gap for a defined set of sites. [982af2ed0756]
6. To fully eliminate mixed content (a prerequisite the source's Chrome-side speaker ties to closing the HSTS-tracking vector, see section 9), expect it to be a multi-stage, multi-month-to-multi-year rollout: run measurement/experiments first to quantify real breakage, then execute a phased cutover, accepting that some legitimate HTTP sub-resource links will simply stop loading. [6d423be1f8d7]

### 3.8 Submitting a site to the HSTS preload list
1. Serve the HSTS header with its `preload` directive set on your production site (this act of serving the header is itself the proof-of-ownership mechanism the process relies on). [982af2ed0756]
2. Submit the domain via the public preload submission process; automated checks verify the site meets requirements before acceptance. [verify UI: exact submission site/URL and current requirements — not given precisely in this source]
3. Before submitting, understand this is very slow and painful to reverse: removal requires waiting through a full Chrome release cycle at minimum, and separately through each OTHER browser's own release cycle for browsers that pull in Chromium's list, so plan preload submission only once you are confident in a durable, long-term HTTPS commitment for the whole domain (and every current and near-future subdomain, if `includeSubDomains` is in effect). [982af2ed0756]

## 6. Tools, settings and named features

- **`rel="noopener"`** on outbound links: prevents an opened tab from getting a `window.opener` back-reference to the page that opened it (tabnabbing defense). Best implemented via a shared link-rendering component so every link gets it automatically. [d749fee9fe72]
- **Cross-origin isolation header** (unnamed with certainty by the source at time of recording; described as "developing," not yet widely supported): isolates a page into its own OS process, disabling `window.opener` and `postMessage`, and incidentally hardening against Spectre/Meltdown-style side channels. [web check: current name — likely `Cross-Origin-Opener-Policy` — the source itself does not commit to a name]
- **"Browser interventions" repository** (GitHub, per presenter, not named precisely): where browser vendors discuss and debate intentionally violating the web spec to protect users, even at the cost of breaking some sites. [web check: exact repo]
- **Google Safe Browsing**: warning categories described — phishing, malware, unwanted software (bundled adware/cryptominers), and a "deceptive"/billing warning for pages that solicit a phone number and covertly bill it. Two APIs described: the naive "Lookup API" (sends the full URL, has privacy/latency drawbacks) and the "Update API" (hash-prefix based, described in procedures above). [a6e67bdd604d] [web check: current Safe Browsing API names/categories]
- **Punycode**: the ASCII (`xn--`-prefixed) encoding browsers render for suspicious/lookalike Unicode domains. [4f89f80a0b9a]
- **Password managers and hardware security keys** (the source describes a Lightning-connector key usable on both computer and phone; general category matches FIDO/U2F/WebAuthn-class hardware keys, though the source doesn't use those exact terms in this part): origin-bound, phishing-resistant credential tools.
- **SameSite cookies**: named explicitly and repeatedly by the source as the concrete fix for the cross-origin image-layout login-state leak (see section 7). [a1ee46e37a85]
- **`spawnSync`** (Node.js): the argument-array-based, escaping-safe alternative to building a shell command string; used as the source's concrete worked fix for command injection. [f4b6df714ffd]
- **SQLite** (via a Node database library exposing `db.get` vs. a general `exec`): `db.get`-style single-row APIs in the source's demo refused to run stacked/semicolon-separated statements, incidentally blocking one class of SQL injection escalation that a general multi-statement `exec` API would have allowed. [478efa2d244c]
- **HSTS response header** and its `max-age`, `includeSubDomains`, and `preload` directives. [05ffb117c836] [982af2ed0756]
- **HTTP Public Key Pinning (HPKP)**: the (now-removed-in-Chrome) dynamic key-pinning header; pins SHA-256 hashes of a certificate's Subject Public Key Info field, never the certificate itself or a serial number. [214a75be3710]
- **CAA (Certification Authority Authorization)**: a DNS record naming which CA(s) are authorized to issue for a domain; advisory, not cryptographically enforced, and undermined by unsecured DNS lookups. [302263a7609a]
- **Static/preloaded certificate pinning**: the smaller, hand-curated, Chrome-binary-baked pin list that was NOT removed alongside dynamic pinning; used for a small set of very high-value sites. [214a75be3710]
- **Certificate Transparency (CT) logs**: public, append-intended logs of issued certificates; described conceptually with Merkle-tree-style cryptographic summaries (mechanics explicitly not detailed by the source). [46771a8e61d2]
- **Googlebot as an incidental CT submitter**: Google's web crawler submits every certificate it observes while crawling to CT logs. [46771a8e61d2]
- **iPhone Touch ID / Face ID**: cited as the concrete example of on-device-only biometric authentication, unlocking a local key store rather than transmitting biometric data. [a55298b2b401]
- **WebAuthn** (named as the subject of the immediately-following guest lecture, not detailed in this part): browser-native API letting sites use device-resident authenticators (fingerprint sensor, Face ID, physical hardware tokens) in a standardized way; cited as already in use at GitHub. ## 8. Mistakes the source warns about

1. Building a shell command or SQL query by string concatenation with any untrusted, request-derived value — the root cause of command injection and SQL injection alike. [d5c07946bb53] [00899c6e9eb7]
2. Using a database query API that supports multiple/stacked statements (e.g., a generic `exec`) when a single-row-returning, single-statement API (e.g., `get`) would suffice — this needlessly widens what an injected value can accomplish (from a read/bypass to a destructive multi-statement attack). [478efa2d244c]
3. Assuming argument-array escaping (fixing command injection) also fixes an over-permissive feature design (e.g., letting a user specify any file path at all) — it does not; these are separate vulnerabilities requiring separate fixes. [45a137425080]
4. Pinning a certificate's serial number or other non-key attribute instead of its actual public key — the source explicitly calls this out as a common mistake in real-world native-app pinning implementations, since a serial number is not cryptographically tied to the operator's identity and is fakeable. [214a75be3710]
5. Restricting certificate issuance geographically/nationally as a fix for CA compromise risk — explicitly rejected by the source as both unenforceable (no clean way to define the boundary) and historically shown not to work (drawing the direct analogy to failed 1990s geography-based email-spam blocking, where most spam turned out to originate domestically anyway, per the presenter's own hedged recollection).
6. Relying on a positive/absence-based security indicator (the padlock icon) as your primary anti-phishing signal to end users — documented as not working reliably in practice. [b6d76d1c801a]
7. Designing any authentication feature that transmits raw biometric data to a remote server rather than using it only to unlock a local key store — biometric data cannot be reset once compromised. [a55298b2b401]
8. Assuming a URL's visual rendering (subdomain graying, punycode display) is a sufficient anti-phishing control on its own — the source documents concrete cases (narrow browser windows, Firefox's homograph gap) where this visual layer fails; origin-bound tooling (password managers, hardware keys) is the layer that keeps working. [4f89f80a0b9a] [8b968c78d019]
9. Shipping HSTS with `includeSubDomains` and a long `max-age` immediately, without a gradual rollout — because HSTS opt-in cannot be quickly undone once cached by real users. [982af2ed0756]
10. Treating (now-deprecated) dynamic certificate/key pinning as still a recommended control — Chrome removed it specifically because of unrecoverable lockout risk (including theoretical "hostile pinning" by an attacker who compromises a server once and then sets a malicious long-lived pin set) and because it depended on client chain-building behavior that server operators cannot reliably predict. [214a75be3710]
