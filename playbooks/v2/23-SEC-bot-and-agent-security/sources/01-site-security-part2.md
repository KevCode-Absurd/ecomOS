## 1. What this source is for

This part continues building the browser-platform mental model a store's engineering side needs, then spends most of its length on two of the most common ways a store's own front end gets weaponized against its own shoppers: Cross-Site Scripting (how untrusted data becomes executed code) and the tracking/fingerprinting ecosystem a store's own third-party analytics and ad tags plug into (which matters for both shopper privacy law and for spotting when a "harmless" embedded script is doing more than the store owner realizes). The closing lecture in this part is a grab-bag of browser-API abuse patterns (UI denial-of-service, popup/window abuse, tab-nabbing) that a store should recognize both as things attackers can do to shoppers via a compromised ad/widget and as things a compromised or careless third-party script embedded on the store's own pages could do. ## 2. Principles

### 2.1 Cross-origin messaging (continuation of part 1's Same-Origin Policy topic)

1. **`document.domain` relaxation is a red flag if found in a codebase, not a technique to use.** Two pages under the same parent domain (e.g. a checkout subdomain and a main-site subdomain) can each set `document.domain` to the shared parent domain to relax the Same-Origin Policy (SOP) and talk to each other directly. The source's explicit instruction: "never use that, forget about it — if you see it, be afraid," because it silently widens trust to every other subdomain that could do the same thing. [Confirms/extends part 1's own explicit warning on this point and card 784.] [784]
2. **The URL-fragment cross-frame messaging trick is legacy/historical, not a current recommendation.** Before `postMessage` existed, a parent frame could pass data to a cross-origin child iframe by repeatedly changing the iframe's URL fragment (`#...`), which does not reload the page; the child polled `window.location.hash` on a timer to read it. Presented purely as "why postMessage exists" history — do not implement this.
3. **Use `postMessage` for any cooperating cross-origin communication, and always set both required checks.** `postMessage(message, targetOrigin)` can send strings or complex objects (structured-cloned, including cyclic references, but not functions or DOM nodes) and supports zero-copy "transferable objects" for large payloads. Two checks are both required, and each protects a different direction: (a) the **sender** must pass the real destination origin as `targetOrigin` (never `"*"`), so the browser itself refuses delivery if the target window's current origin doesn't match — this also protects against the target frame having been silently navigated elsewhere since it was referenced; (b) the **receiver** must validate `event.origin` against an expected origin/allow-list inside its `message` listener before trusting `event.data`. The source stresses check (b) is easy to forget, because unlike `targetOrigin` (a required call parameter — omitting it errors), the receiver's origin check is just an `if` a developer must remember to write; nothing errors if it's missing. [796]
4. **A missing sender-side origin check on `postMessage` can leak personal data to any embedding site.** Worked failure: a page (e.g. an account page) embeds another page (e.g. a login/identity page) in an iframe expecting it to `postMessage` back the logged-in user's name; if the identity page posts that message without restricting the destination, ANY site on the internet can embed it in an iframe and passively learn who is logged in and their name — usable for cross-site tracking/deanonymization. `[applying source's general web rule to e-commerce: a "who's logged in" widget or an embedded account-status iframe on a storefront must specify its exact postMessage targetOrigin, never broadcast to any parent.]` [796]
5. **A missing receiver-side origin check on `postMessage` lets any page that can obtain a window reference spoof trusted messages.** Worked failure: a page listens for a "here is the username" message from an embedded identity iframe and trusts whatever it receives; if that listening page can itself be framed or opened as a popup by an attacker (i.e. it does not prevent being framed — see clickjacking, principle 2.6 below), the attacker gets a reference to its window and can send it a forged message impersonating the identity page's expected payload. Fix: always check `event.origin` before trusting `event.data`. [796]
6. **Transitive trust in `postMessage` has no technical fix — it is a trust decision, not a bug.** If a site legitimately shares data via `postMessage` with a second, trusted site, and that second site's own security is weak, the originating site cannot control what happens to the data afterward. The source explicitly does not offer a fix for this case beyond "at that point you're trusting them" — keep the list of sites you `postMessage` sensitive data to as short as the business need allows. [796]
7. **Several cross-origin embeds are allowed by default and carry "ambient authority" (automatically attached cookies) — this is the root of several attack classes covered later in this part.** Cross-origin `<img>`, `<link>` (CSS — this is how Google Fonts works), `<script src>`, and cross-origin form submission are all allowed by SOP by default. Critically, a cross-origin `<script src>` executes **in the including page's own origin/context**, not the origin it was fetched from — "as if you pasted the code into this page" — which is exactly why a CDN-hosted library like jQuery can manipulate the including page's DOM, and exactly why including any third-party script is a full-trust decision: a malicious or compromised script host can run arbitrary code with the including page's full privileges. `[applying source's general web rule to e-commerce: any third-party script tag on a storefront — analytics, chat widget, review widget, ad pixel — runs with the full privileges of the storefront page itself, including access to session cookies readable via JS and the DOM of the checkout page if not isolated in an iframe.]` [0cc21dc1fdd0] [917]

### 2.2 Ambient cookie authority, SameSite, Referer/Referrer-Policy, and the cookie/SOP mismatch

8. **Cross-origin embeds silently carry the browser's ambient session cookie, which can leak personalized content.** Worked example: attacker.com embeds `<img src="https://target.com/avatar.png">` where target.com serves the logged-in user's personalized avatar at that URL; the browser auto-attaches target.com's session cookie to the image request, so target.com's server treats it as a logged-in request and returns the real, personal avatar into the attacker's page — usable to make a phishing page look convincingly personalized. `[applying source's general web rule to e-commerce: a personalized "welcome back" image, avatar, or account-status asset served at a fixed, cookie-gated URL is embeddable and readable in exactly this way by any other site unless the cookie is SameSite.]`
9. **SameSite cookies are the reliable fix for ambient-authority leaks via cross-origin embeds, not Referer checking.** If the cookie is set with `SameSite`, a request for the same resource made from a cross-site page will NOT include the cookie, so the server returns whatever it serves to a logged-out/anonymous request. Two modes named without detailed behavioral differentiation in this part: "Lax" and "Strict" (see part 1 and card 1b76024d8b1a for the fuller Lax-vs-Strict guidance). [f4015dad3b23] [1b76024d8b1a] [0279d922e722] [c2bad816cf64] [05aa24ef18f6]
10. **Referer-based access control is unreliable for two independent, compounding reasons — do not rely on it as a security boundary.** (a) Browser HTTP caching does not vary a cached resource by Referer by default, so once a resource has been legitimately fetched and cached, a later cross-site request for the SAME cached resource never even reaches the server, and any server-side Referer check on it never runs — the defense is silently bypassed by the cache, not defeated by an attacker doing anything clever. (b) Independently, `Referrer-Policy` lets the **linking site itself** suppress or truncate its own outbound Referer header for privacy reasons (see principle 12), so a defender cannot assume Referer will even be present. Weaker mitigations mentioned for the caching half of the problem: vary the cache by a specific header, or mark the resource non-cacheable so every load actually reaches the server (this does not fix problem (b)). [332f8d82f1e1] [be4fc9dfbd67]
11. **CDN cache-sharing across sites is a deliberate, desirable trade-off — do not "fix" it by keying cache on Referer.** The same browser caching behavior that breaks Referer-based defenses is also why loading a shared library (e.g. jQuery) from a common CDN is fast: many unrelated sites embedding the identical script URL let the browser reuse one cached copy across all of them, which is the whole point of using a CDN for shared, non-sensitive static assets.
12. **`Referrer-Policy` is a site-level header a linking page sets to control what Referer is sent when its own links are followed or its own sub-resources are requested — set it deliberately for pages holding sensitive/capability URLs.** Old default: `unsafe-url` (always send the full referring URL). Newer/current default (as of this recording): send the full URL only when navigating same-origin, and suppress Referer entirely on an HTTPS-to-HTTP (secure-to-insecure) navigation, because an HTTP request is visible in plaintext to anyone on the network path. Other values let a page send only its origin (no path) cross-origin, or nothing at all. Worked example: Google Docs is described as using a referrer policy so that clicking a link from within a document does not leak the document's own (capability-bearing, effectively-secret) URL to the linked site — `[web check: current Google Docs Referrer-Policy value, since the source's specific breakdown was the lecturer's own inference, not confirmed]`. `[applying source's general web rule to e-commerce: any page carrying a sensitive or capability-style URL — a password-reset link, an order-status link with an embedded token, an unsubscribe link — should set a Referrer-Policy that does not leak that URL to whatever site the shopper clicks through to next.]` [6e1a3962fe72]
13. **Cookie scoping and SOP use different, conflicting trust models — this mismatch is a recurring root cause, not a one-off bug.** Cookies can be scoped to a `Path`, but this is not a real security boundary — any same-origin frame/script can still read cookies set for the whole origin regardless of path. Simultaneously, cookies are *less* restrictive than SOP: a more-specific host (e.g. `attacker.stanford.edu`) can set/overwrite cookies for a broader parent domain (`stanford.edu`) even though these are different origins under SOP — "more specific names can mess with less specific names" for cookies, unlike origins, which must match exactly. [d721b7f8d72e] [4388ab8bc2f2] [a88d4d33040c]
14. **This cookie/SOP mismatch compounds a DNS hijack into a domain-wide cookie compromise.** Recapping and extending part 1's DNS-hijacking material: if an ISP or attacker intercepts a mistyped/non-existent domain lookup (NXDOMAIN) and serves a substitute page (e.g. an ad-injection page) on that misspelled host, and that substitute page has its own vulnerability that lets attacker script run in that hijacked-domain context, the cookie-scoping mismatch above means that script can read AND set cookies for any real domain a subdomain relationship allows it to affect. Named mitigation: enforcing HTTPS site-wide prevents this class of interception, because an ISP/on-path attacker cannot transparently substitute a page for an HTTPS destination the way it can for an HTTP/DNS-level redirect. [Extends part 1's DNS-hijack cards 2117b632489b, cc819036c4e0.]

### 2.3 A full "can site A do X to site B" hardening table (Same-Origin Policy, made concrete)

15. **Linking to another site cannot be reliably prevented.** No mechanism requires reciprocal consent for a hyperlink. Best-effort only: a server can inspect the incoming Referer header and respond differently to visitors referred from a known site, but a linking site can suppress its own Referer via `Referrer-Policy` (principle 12), defeating this entirely. This matters for SEO/reputation risk (search engines weigh inbound links, so a store can be penalized by low-quality sites linking to it with no recourse) but has no security fix.
16. **Embedding your site in a frame IS reliably preventable, and doing so closes an entire attack family (clickjacking) — treat this as a required control, not optional hardening.** See principle 2.6 below for the mechanism (a "deny framing" / "same-origin-only framing" response header) and why it is one of the few controls in this whole table the source calls fully reliable. [833] [f40756f20bb7] [929]
17. **A site can never reach into an embedded site's DOM and modify it, by SOP default, and there is no way to relax this.** Stated explicitly by the source as the one row in this table that cannot be turned into a "yes" even intentionally.
18. **Form submission to your site cannot be blocked outright, but you can reliably filter or de-authenticate it.** Any site can submit a form (GET or POST) to your site by default. Two reliable controls: check the browser-set `Origin` request header (present on cross-origin, non-simple/CORS-relevant requests — see caveat in principle 19) against an allow-list to reject unwanted submitters outright; or use SameSite cookies as a middle ground that still lets the form arrive but strips the session cookie, so it cannot act as an authenticated request. [d0eca305c2e6] [253ee935eb07]
19. **The `Origin` header cannot be spoofed by the requesting page, but it is not sent on every request.** The browser sets `Origin` and the requesting page's own script cannot manipulate it — a server can trust it fully for the requests that carry it. Caveat: plain GET requests for images/scripts/styles are never treated as CORS-relevant and typically do not carry an `Origin` header, so Origin-based blocking works for POSTed forms/CORS-relevant requests but not for hotlinked image/script GETs — Referer (unreliable, principle 10) is the closer analog for those.
20. **Hotlinked images and scripts cannot be reliably blocked** — this is allowed by SOP default with no fully reliable fix. Referer-based blocking is possible but shares the unreliability of principle 10. Practical mitigation offered specifically for the "leak a personalized image" case (not general bandwidth-theft hotlinking): serve the image at an unguessable, per-user URL rather than a predictable one, so an attacker cannot construct the request even though the browser would happily send it. `[applying source's general web rule to e-commerce: a per-customer loyalty badge, order-status image, or personalized banner served at a guessable URL pattern is hotlinkable and, combined with ambient cookie attachment (principle 8), potentially leakable — use unguessable tokens in the URL, not sequential/predictable customer IDs.]`
21. **Reading the byte-level response data of another site is denied by default, and is the ONE row that can be intentionally relaxed for cooperation — this is what CORS exists to do.** "Reading data" here means a script obtaining the actual response bytes as a JS value it can inspect (e.g. `fetch`-ing a JSON API response into a variable, or extracting pixel/byte data from an image/PDF) — distinct from merely displaying/embedding that content visually, which is generally allowed. `postMessage` (principle 3) only works between two cooperating PAGES with a listener; it cannot be used to read an arbitrary API's JSON response, since there is no page/listener on the other end to message with. [This sets up JSONP (2.4) and, per the source's own framing, real CORS headers — CORS mechanics themselves are not reached within this part; check part 1 or part 3.]

### 2.4 JSONP: the legacy workaround for reading cross-origin API data, and why it is risky

22. **JSONP works because `<script src>` requests are exempt from SOP, but a bare JSON response is not valid, capturable JavaScript on its own.** A bare JSON object literal at the top level of a script is not valid standalone JS (it parses as a labeled block statement, then hits a syntax error at the colon); even if it were valid, executing a script only produces side effects — there is no way to capture a "return value" from a `<script src>` load.
23. **JSONP's actual mechanism: the consumer tells the provider a callback function name; the provider wraps its JSON in a call to that name.** Site A defines a function (e.g. `handleTime`) and requests `https://siteB/api/time?callback=handleTime`; site B, if it supports JSONP, responds with `handleTime({...json...})`, which is valid, executable JavaScript that delivers the data as a function argument when the `<script>` tag executes. [4b7cd675a290]
24. **JSONP has two independent, serious downsides — the source recommends against it (headers or a server-side proxy instead).** From the data-provider's side: naive string concatenation of the user-controlled callback name into the response is an injection risk (an unsanitized callback parameter can be used to inject arbitrary JavaScript, which the source names as the cause of a "reflected file download" attack, detail deferred to elsewhere in the course); some strings that are valid JSON are not valid bare JavaScript (a cited class: certain whitespace/line-terminator characters), so naive wrapping can also produce broken output. From the data-consumer's side: to fetch "just a bit of data," the consumer must include a `<script>` tag from the provider, granting the provider (or anyone who compromises the provider's server) full code-execution privileges on the consumer's own page — equivalent to a self-inflicted supply-chain XSS if the provider is ever compromised. `[applying source's general web rule to e-commerce: never use JSONP to pull data from a partner/affiliate/marketplace API into a storefront page; a proper CORS-enabled endpoint or a server-side proxy call keeps a compromised partner API from getting script execution on the storefront.]` [4b7cd675a290]
25. **A rejected but instructive alternative: server-side proxying/scraping.** Site A's own server fetches site B's data and re-serves it to A's users from A's own origin — this sidesteps SOP entirely (it is not a browser cross-origin request) and works fine for non-personalized data, but the source explicitly rejects it as the general solution because it cannot represent a response that depends on WHICH USER is asking (e.g. per-login/personalized API data) — a purely server-to-server proxy has no way to authenticate as the end user to the third party.

### 2.5 Clickjacking and framing defenses

26. **Clickjacking mechanics: an invisible, correctly-positioned iframe intercepts a real click on the real site underneath a decoy.** The attacker embeds the victim site in an iframe, positions it with CSS over a decoy element on the attacker's own page so a known, predictable victim-site button (the source's example: an e-commerce "Buy Now"/bid button) lines up under the decoy, and sets the iframe's CSS opacity to 0. The victim sees the decoy but the click actually lands on the real, transparent, topmost victim-site button, using the victim's own real, authenticated session — this works identically over HTTP or HTTPS; the only precondition is that the victim site allows itself to be framed at all. `[applying source's general web rule to e-commerce: an unprotected checkout/cart/"add to cart"/account-settings page can be clickjacked into performing a purchase, quantity change, or address/settings edit the shopper never intended, via a decoy overlay on an unrelated page.]` [014e55d2af7f] [63b312e58f7d] [f40756f20bb7]
27. **SameSite cookies also mitigate clickjacking, in addition to CSRF.** A clickjacked click delivered via a cross-site iframe is a cross-site request; with SameSite cookies, the session cookie is not attached, so the click lands as logged-out and the intended action does not execute as an authenticated user. Real-world example cited: Facebook "Like"-button clickjacking, where clickbait sites overlaid an invisible Like button over a fake "play" button, and attackers also used CSS transform/zoom to blow up a single button to cover an entire page, guaranteeing any click hit it.
28. **Frame busting (client-side JS checking `window.top` and trying to navigate the whole browser back to itself) is a deprecated, broken defense — do not rely on it.** A cited Stanford research paper ("Busting Frame Busting," roughly 10 years before this recording) found essentially every known frame-busting technique could be defeated (example bypass given: using the `beforeunload` event on the top-level page to intercept and cancel the frame-buster's attempted navigation).
29. **The reliable, current defense is a "deny framing" / "same-origin-only framing" HTTP response header, read and enforced by the browser.** [Source describes exactly X-Frame-Options `DENY`/`SAMEORIGIN` mechanics without using that literal header name in this transcript excerpt; treat as that header or its CSP `frame-ancestors` successor — `[web check: current recommended header/value, since CSP frame-ancestors has superseded X-Frame-Options in modern guidance]`.] The server always responds normally (it cannot reliably tell who is asking); the BROWSER reads the header on the response and, if framing is disallowed for this context, discards the response and renders an empty frame instead. This protects a legitimate browser/user; it does not stop someone attacking their own account with a custom/hacked browser (never a goal — server-side defenses exist to protect legitimate browsers/users from OTHER malicious pages). Browser-support caveat (general principle for any browser-enforced defense): check the market share of browsers implementing a given header before relying on it alone; for anti-framing specifically, the source says support has been broad and long-standing enough to rely on. `[web check: current browser support]` [c3411ca931e1] [929]
30. **The framing-defense check must cover the entire ancestor chain, not just the immediate parent frame — verify your browser support assumption.** Older browsers only checked the immediate parent's origin against a "same-origin-only" framing policy, so a chain like target.com -> untrusted-third-party.com -> target.com passed (the innermost and outermost frames share an origin, even though an untrusted origin sits in between) — worked historical example: MySpace embeds an untrusted ad, which itself embeds another copy of MySpace; the old check passed and let the ad wrap a real MySpace frame for clickjacking. Modern Chrome and Firefox (per the source; other browsers not confirmed) now check the FULL ancestor chain. `[web check: whether all current major browsers do full ancestor-chain checks]`
31. **Recap table for hardening the SOP against another site (useful as a literal reference table):** link to you — cannot be reliably prevented; embed you in a frame — CAN be reliably prevented (recommended); reach into an embedded frame's DOM — never allowed, and cannot be relaxed either; submit a form to you — reliably preventable via `Origin` header allow-listing, or de-authenticated via SameSite cookies; embed your images/scripts — allowed by default, no fully reliable block (unguessable URLs help for the personalization-leak case only); read your byte-level response data — denied by default, and the only row intentionally relaxable for cooperation (CORS).

### 2.6 Cross-Site Scripting (XSS): root cause, worm case study, and reflected-XSS mechanics

32. **XSS and SQL injection are the same root-cause bug class: untrusted data interpreted as code because it was concatenated into a code context without being neutralized.** The source draws this parallel explicitly in passing (SQL injection is covered fully elsewhere in the course, not in this part). [79e6ed7e0b84]
33. **Stored XSS is a self-propagating worm risk in any user-generated content field a store renders unescaped — the Samy/MySpace case study, presented as illustrative history, not exploit code.** Samy Kamkar (2005) found he could embed executable script in his MySpace profile's free-text field; anyone who merely VIEWED his profile ran the script, which (a) silently added Samy as their friend and (b) copied the same payload into the VIEWER's own profile, self-propagating to everyone who viewed an infected profile — and separately injected arbitrary visible text ("Samy is my hero") into every infected profile. Worked growth numbers (source's own example, not a general rate): 73 friends at start; ~1 hour later, 1 new friend request; ~7 hours later, 221; roughly another hour, ~442; another hour, ~500-ish plus angry messages from added users, who were RE-ADDED automatically simply by viewing their own re-infected profile again; ~5 hours further, "almost a million"; final anecdote, "refreshed in three seconds, gained about a thousand friends, then a couple seconds later, over a million." MySpace went down for "a few hours" for maintenance, likely (source's own inference) from the load multiplier of every profile view triggering extra requests; the payload was later removed, likely via a database-wide strip, but residual "Samy is my hero" text remained afterward. `[applying source's general web rule to e-commerce: any customer-facing free-text field a store renders back to OTHER shoppers unescaped — a product review, a Q&A answer, a public wishlist name, a seller/vendor profile bio on a marketplace — is a stored-XSS worm vector with exactly this self-propagation shape if it can also write to that same field.]` [0046b75dd217]
34. **The goal of XSS is to get attacker JavaScript to run IN the origin of the site being attacked, because SOP otherwise blocks reaching into that origin from outside.** An attacker cannot frame a bank's (or store's) site and attach a listener to its real login/checkout form from a different origin; XSS is the way around that boundary when the vulnerable site itself can be tricked into serving attacker script as if it were the site's own code.
35. **Two concrete capability classes an XSS payload gets, both already covered generally in part 1 and reiterated here specifically for XSS:** (1) take actions AS the logged-in user, forging authenticated requests with the ambient session cookie (Samy's payload POSTed a real "add friend"/profile-modify request the server could not distinguish from a genuine user action); (2) steal the session cookie directly via `document.cookie` (a plain string) and exfiltrate it to an attacker server, letting the attacker set the same cookie in their own browser and fully impersonate the victim, no password needed.
36. **Reflected-XSS worked demo mechanics (search-page example), described defensively:** naive server code reads a query parameter straight off the URL and string-concatenates it, unescaped, into a server-rendered HTML template. Browser URL-encoding on form submission (turning `<`, `>`, `=`, spaces, etc. into `%XX` sequences) is transport-layer only and fully reversible by the server — it provides NO XSS protection once the server decodes it back and concatenates the raw string into HTML. If the parameter contains a `<script>` payload, the assembled response contains it literally inline, and the browser cannot distinguish "HTML the developer wrote" from "attacker data the developer forgot to neutralize" — both are just bytes in the same HTTP response. [7bec48d403c6]
37. **Testing convention: use a harmless `alert(document.cookie)` payload to prove an XSS hole exists without doing real damage.** This "only attacks yourself" (you're just displaying your own cookie back to yourself); a real attacker would instead have the script silently exfiltrate the cookie, e.g. by creating an `<img>` pointed at `attacker.com/steal?cookie=...`, causing a GET request that carries the stolen value with no visible UI feedback to the victim.
38. **Denylist/pattern-blocking untrusted input for XSS is a fragile, insufficient defense — the fix is output escaping, not input rejection.** Rejected approach: refuse or error on input containing `<script>` or similar patterns; critique: a single missed variant/encoding breaks the whole defense, and it can over-block legitimate use (source's own anecdote, presented as illustrative and unverified: some banks reportedly forbid usernames that "sound programmer-ish" like `script`, `select`, `insert` — explicitly warned NOT to be relied on as the actual control). Correct fix: HTML-entity-escape untrusted data at the exact point it is inserted into an HTML context (`<` -> `&lt;`, `>` -> `&gt;`, etc.), applied ONLY to the untrusted value, never to the whole page. In real projects, use the templating/view layer your framework provides (named examples: EJS, Jade) rather than calling an escape function by hand; most such layers also expose an explicit, deliberately scary-sounding "raw"/unescaped opt-out — use it only when certain the value is not attacker-controlled. [2df9b830a02e] [0393d1e220fb] [1ffc9074018e]
39. **Reflected-XSS delivery relies on tricking the VICTIM into loading a crafted URL to an otherwise-trusted, logged-in site — "don't click suspicious links" is not a sufficient user-side defense.** The payload lives in the URL of a site the user already trusts and is logged into; the vulnerability is server-side, not a matter of user judgment about the domain. This is worse on mobile, where many clients/apps/shorteners hide the full URL, so "inspect the URL first" is weaker in practice than it once was on desktop.
40. **XSS prevalence claim (dated, flag before citing):** the guest-lecture-adjacent course material cites a "White Hat Security" industry report (source: roughly 2015-2016) finding about half of tested sites had an XSS problem, with XSS long ranked at or near the top of vulnerability-prevalence lists; percentages sum over 100% because sites commonly have multiple vulnerability classes. The instructor's own added opinion (flagged as such): XSS remains just as prevalent because client-heavy frameworks (React, etc.) introduce new DOM-based XSS patterns the ecosystem "hasn't figured out ways of solving well yet." `[web check: current prevalence data — this stat was already 3-4 years old at recording time]`
41. **Restated core principle: never trust the client.** Any data from the browser/user is suspect and must be cleaned before use in ANY code context — HTML, JavaScript, SQL, or otherwise.
42. **Two formal XSS types (a third is named as coming later in the course, not detailed in this part):** Reflected XSS — the payload lives in the HTTP request itself (URL path/query/etc.); requires getting the specific victim to load a crafted link; limited to whatever request-derived value the server unsafely echoes. Stored XSS — the payload is persisted server-side (e.g. in a database), so it is served to ANY visitor regardless of what URL they used to arrive; the source stresses stored XSS is more powerful precisely because the INJECTION VECTOR can be anything the server later reads and re-renders (worked hypothetical: even a value taken from an HTTP request header, which a victim would never naturally trigger by clicking a link, still yields stored XSS if the attacker directly crafts one request with that header themselves — the victim only has to VIEW the page later, not click anything at injection time). "It doesn't matter how you get the attack code into the database." [7bec48d403c6]

### 2.7 Per-HTML-context escaping rules and never-safe contexts

43. **Escaping rules differ per syntactic context, and getting even one context wrong breaks the whole defense — this is why XSS remains hard.** The web nests many languages (HTML containing JS containing string literals containing further data), each with its own control characters and rules.
44. **Plain HTML text-node content: escape `&` and `<` together — this is the simplest, most reliable case, with an explicit carve-out.** Escaping only `<` is insufficient, because a user who legitimately typed the literal characters `&lt;` would have it double-interpreted back into a real `<` on render; escaping `&` (to `&amp;`) and `<` (to `&lt;`) together is sufficient for ordinary tag content. Explicit exception carved out: `<script>` and `<style>` contents follow completely different rules (see principles 48-49 below). [6ee053ebfcc9] [1ffc9074018e]
45. **Quoted HTML attribute values: escape BOTH quote characters, always.** Unescaped, an attacker can include a literal quote to terminate the attribute early and inject a whole new attribute (e.g. an event handler) onto the same tag. Because HTML attributes may legally use either single or double quotes, escape both regardless of which the template uses; over-escaping (turning any character into an entity even where not strictly needed) is explicitly harmless from the browser's rendering perspective. `[applying source's general web rule to e-commerce: a shopper-supplied display name rendered into an `alt=` attribute on their own avatar/review image is exactly the worked stored-XSS case the source gives — anyone who views that shopper's profile/review runs the injected code.]` [6ee053ebfcc9]
46. **Never use unquoted HTML attribute values — the safe character set to escape is unmanageably large.** Browsers use a surprisingly permissive/"lax" parser for where an unquoted attribute value ends; far more characters than a plain space will terminate it and let an attacker start a new attribute, so escaping only quotes (or only a space) does nothing when there are no quotes present. The concrete recommendation is absolute: always wrap attribute values in quotes, eliminating this class of problem outright rather than trying to enumerate every lax-parser delimiter. Historical note: unquoted-attribute parsing rules used to differ across browsers entirely; now standardized, but still called "a bad idea." [1099]
47. **"Powerful" attributes (`src`, `href`) need scheme/well-formedness validation, not just quote-escaping — this is a structurally different vulnerability.** Escaping quotes does not help, because the danger is not attribute breakout — it is that the attacker fully controls WHERE the browser fetches/navigates. Two dangerous URL schemes named: `data:` URLs (embed a full synthetic response, including MIME type and body, directly in the URL — e.g. `data:text/html,<script>...`; legitimate small-asset-inlining use case exists — see principle 51 — but dangerous when user-controlled in `src`/`href`; the source explicitly does not know and flags as unresolved what ORIGIN a `data:`-URL iframe is treated as, `[web check: origin behavior of data: URL iframes/navigations]`); `javascript:` URLs (navigating to `javascript:<code>` executes `<code>` in the CURRENT page's context rather than navigating; legacy mechanism, essentially no legitimate reason to use it deliberately today, survives for backward compatibility). Guidance: validate that any user-influenced `src`/`href` value is well-formed AND restricted to expected schemes (e.g. `http`/`https` only) before use, in addition to quoting/escaping. [95fe4dae87431] [1099]
48. **`javascript:` URLs are a live social-engineering (phishing) vector, mitigated but not eliminated by browsers stripping pasted prefixes.** A well-known pattern (source calls it "a common meme," e.g. fake "paste this to see who viewed your profile" posts) tricks a victim into copy-pasting an attacker-supplied `javascript:`-prefixed string directly into their own browser's address bar, running the attacker's code with full access to whatever page/session is open. Chrome and Firefox (per source) automatically strip a pasted `javascript:` prefix as a friction/"roadblock," not a full fix (a user can manually re-add the stripped prefix and it still works); Safari blocks JS execution from the address/search field by default with a settings toggle to re-enable. `[web check: current browser behavior for pasted javascript: URLs]`
49. **Escaping data placed inside an inline `<script>` block's JS string requires MULTIPLE layers, and even then the closing `</script>` tag itself cannot be neutralized by JS-level escaping — hex-encoding or the `<template>` tag are the only fully safe options.** Progressive worked failures: (a) escaping only quotes (`\'`, `\"`) fails if attacker input contains a literal backslash immediately before a quote, since an attacker-supplied `\` can combine with the escaper's own inserted `\` to "un-escape" it — fix: also escape literal backslashes to `\\` first. (b) Even after backslash-escaping, HTML PARSING happens BEFORE JavaScript parsing, and the HTML parser looks for the literal (case-insensitive) text `</script>` to find the end of a script element WITHOUT understanding JS syntax at all — it does not care whether that text sits inside a JS string or comment. So if attacker-controlled data anywhere inside a `<script>` block contains the literal characters `</script>`, the HTML parser terminates the enclosing script tag right there regardless of any JS-level escaping, and the attacker can follow it with an entirely new, valid `<script>...</script>` block of their own. Fix 1 (hex-encoding): encode all untrusted data destined for an inline script context using only hex digits (`0-9a-f`) before embedding it, then decode it back to the real value at runtime in JS — closes off quotes, backslashes, and `</script>` all at once, since none of those characters can appear in a pure hex string; the source notes this correct approach is under-used in real code. Fix 2 (the `<template>` tag): place untrusted data inside an inert `<template>` element using only the simple text-node escaping rule (`&` and `<`, principle 44), then retrieve it at runtime via `document.getElementById(...).content` rather than ever putting it directly into executable script source — avoids the whole script-context escaping problem by keeping the data out of any script-parsing context in the first place. [c9669d9997786] [48e61c95a937]
50. **The DOM automatically creates a global JavaScript variable named after any element's `id` attribute — letting a user control an `id` lets them declare/override globals a trusted script did not expect.** This is a DOM behavior, not a JavaScript-language fault. Worked risk: if an attacker/user controls an element's `id` (e.g. a rendered profile field), they can make a normally-`undefined` variable check evaluate truthy, silently diverting an otherwise fully safe, developer-written script down an attacker-chosen code path — no escaping scheme fixes this; the fix is not letting user data determine element `id` values (or attribute NAMES generally — see principle 51).
51. **A short, explicit list of contexts that are NEVER safe for untrusted data, regardless of escaping attempted — avoid placing user data there at all:** free-floating/bare code directly executed as a JS statement inside a `<script>` block (this is direct code execution, not an escaping problem); HTML comments (the source says the actual parser termination rules are unusually hard to enumerate correctly, and there is no legitimate reason to put user data in a comment anyway, since comments aren't rendered); HTML tag names (denylisting tag names like `script`/`style` is unreliable — see parser-leniency bypasses below); attribute names; and cell contents (named in passing, no further detail given). [1ffc9074018e]
52. **HTML's lenient/"forgiving" parser is itself a security liability, because it defeats denylist/pattern-based filters trying to catch dangerous tag or attribute syntax.** Concrete quirks cited: a slash where whitespace is expected between a tag name and its first attribute can be silently treated as a space (letting `<script/src=...>`-style constructs parse identically to `<script src=...>` and bypass a filter looking for a literal trailing space); Firefox (at time of recording) ignored various unexpected characters between an attribute name and its `=` sign, letting junk characters defeat a filter looking for an exact string like `onload=` while the real parser still executes it as `onload=`. General lesson: any denylist/pattern-matching defense against dangerous HTML syntax is unreliable, because the real browser tokenizer is far more permissive (and historically inconsistent across implementations) than any hand-written pattern is likely to anticipate.
53. **The "robustness principle" (be lenient in what you accept, strict in what you produce) explains WHY HTML parsing is this lenient, and the source explicitly argues it is bad for security.** Historical rationale (from network protocol design, e.g. TCP): accepting slightly malformed input from other systems improves real-world interoperability. Concrete historical example: early Internet Explorer silently "fixed" malformed HTML (e.g. auto-closing unclosed tags); when Firefox later tried strict spec compliance, real pages (built and tested only against IE's undocumented leniency) broke, forcing Firefox to reverse-engineer and copy IE's specific buggy leniency just to render existing sites the same way. Source's stated conclusion: this is "actually bad" for two reasons — it forces every implementation to GUESS at ambiguous/malformed input rather than reject it (creating exactly the parser-quirk attack surface above), and it entrenches undocumented vendor-specific quirks as de facto requirements other implementations must copy, instead of surfacing errors early so authors fix their own broken markup. Preferred alternative (source's opinion): fail/error immediately on malformed input.
54. **Summary rule: only three contexts have a reliable, simple escaping approach — everything else needs a specialized technique or must be avoided entirely.** The three safe-by-simple-escaping contexts: plain HTML text-node content (principle 44); quoted HTML attribute values (principle 45); and content placed inside a `<template>` tag retrieved via JS (principle 49). Everything else covered in this part — unquoted attributes, `src`/`href`/dangerous-scheme attributes, inline JS string/event-handler contexts (without hex-encoding or the `<template>` workaround), HTML comments, and tag/attribute names — is either unsafe outright or requires a non-trivial specialized technique (hex-encoding, scheme validation, or moving the data out of the dangerous context). [1ffc9074018e]
55. **Deeply nested contexts require re-escaping at EVERY layer, in the correct order — avoid writing this pattern at all.** Worked example: user data inside a JS string literal, itself the argument to `setTimeout(...)`, itself the value of an inline `onclick` HTML attribute — each layer is parsed and re-interpreted SEPARATELY and at DIFFERENT TIMES (HTML parser reads the `onclick` value as a plain string first; on click, that string is parsed as JavaScript; the `setTimeout` argument string is parsed as JavaScript again later when the timer fires), so the data must be escaped correctly three separate times (two rounds of JS-string escaping plus one round of HTML-attribute escaping) in the exact right composition/order. Explicit, strongly worded guidance: never write code with this nesting shape, even though the source notes it is "surprisingly common" in real codebases. General corollary: escaping applied for one context is never automatically valid for a DIFFERENT outer context the same value later gets placed into — re-apply fresh escaping for every context boundary crossed.
56. **[Flagged as unresolved/incomplete within this part — likely covered elsewhere in the source]:** the source promises but does not detail (within this part) a Chrome feature called "XSS Auditor" — described only as: it detected when a request URL contained script-like content also appearing verbatim in the server's resulting HTML response (a heuristic for reflected XSS) and tried to strip/neutralize that script automatically; the source explicitly flags this well-intentioned mitigation as having paradoxically enabled NEW attack classes, with specifics "next time" (i.e. presumably a different part of this source). [825a61a6a5f9]

### 2.8 Web tracking and browser fingerprinting (guest lecture: Pete Snyder, Brave/W3C)

57. **Third-party ad networks shifted ad-targeting from matching ads to CONTENT to matching ads to a tracked PERSON — this shift is the technical root of most modern cross-site tracking, per the guest speaker's own historical framing.** Early web ads (and earlier print ads, and "web rings" of self-identified same-topic sites) matched ads to page/content topic; the shift to third-party iframe-served ads let a small number of third parties accumulate cross-site behavioral profiles of individual people, independent of any single page's content. Source's own economic analysis (explicitly his framing, not a cited study): once ads can follow a PERSON rather than a page, advertisers can reach the same audience via many cheap, low-quality sites as easily as via one respected high-quality site, shifting ad revenue away from high-quality publishers toward high-volume, lower-quality ones, because the marginal cost per audience member is lower on cheap sites even when the premium site's absolute traffic/revenue is still higher. [Speaker's own economic opinion, explicitly disclaimed as non-political — treat as framing, not a cited finding.]
58. **Real-world harm example cited (Target's pregnancy-prediction incident):** widely known incident (recounted informally, no technical detail given in this part) where Target's purchase-pattern-based marketing inferred a teenage customer's pregnancy and sent maternity marketing to her home, revealing the pregnancy to her father before she had told him — used to illustrate that behavioral-tracking harms extend beyond ad-revenue effects into serious individual privacy/safety harms. `[web check: exact details if cited precisely elsewhere; this part gives no technical mechanism, only the anecdote]`
59. **Tracker-prevalence research (Englehardt & Narayanan, Princeton, cited paper, numbers explicitly dated by the speaker):** a crawl of roughly one million websites measuring third-party resource requests found the median/average site had roughly 20 distinct third parties with technical visibility into that visit (not all classified as active "trackers" — e.g. CDNs with contractual no-tracking commitments, like the source's example Fastly, are counted separately as merely capable, not confirmed trackers). Google (aggregating Google Analytics, Fonts, Maps, etc. as one organization) was present on roughly 70-80%+ of measured first-party sites in the cited (dated) data — described as meaning Google has the technical vantage point to record visits to the large majority of the open web's first-party sites, with no way for ordinary users to view, audit, or delete that record. `[web check: current tracker-prevalence numbers — already called "a little out of date" by the speaker at recording time, and older still now]` [223a113427af] [89687968a429]
60. **First-party / third-party / eTLD+1 definitions (reference vocabulary, same eTLD+1 concept underlying SameSite cookie site-boundary determination):** "first party" = generally the top-level domain the user navigated to; "third party" = any other origin whose resource loads within that page. TLD = top-level domain (`.com`); eTLD = "effective TLD," accounting for compound public suffixes like `.co.uk`; eTLD+1 = the registrable domain one label below the effective TLD (e.g. `cnn.com`, or `example.co.uk`) — the standard heuristic for grouping subdomains as "the same site" for both tracking-measurement and cookie-scoping purposes. Classification gets ambiguous when third-party CODE executes inside a first-party page/frame (can be attributed to either party depending on measurement methodology).
61. **Third-party cookies are, per the speaker's own estimate ("not 100% true but... to a first approximation 90% of the trouble"), the primary technical mechanism enabling cross-site tracking at scale, and this arose from a largely accidental, rushed 1990s spec decision — not a deliberate design.** Historical/mechanistic background: HTTP's original stateless model needed a way to carry session state (native HTTP auth exists but is "pretty crummy" and essentially unused, per the speaker — "literally only the W3C's own site" allegedly still uses it, an anecdotal claim); cookies (a server-issued token echoed on every subsequent request) solved this legitimately. Independently, 1990s bandwidth costs made cross-domain asset-sharing common (image hosting on other servers). The pivotal, largely accidental decision when the cookie spec was being rushed: whether to send cookies along with these cross-origin resource requests too — the answer was yes, enabling a tracker whose resource is embedded on many unrelated sites to recognize the same browser across all of them via its own, consistently-resent cookie. `[applying source's general web rule to e-commerce: any third-party pixel, widget, or analytics/ad tag embedded on a storefront is a candidate for exactly this cross-site tracking mechanism, whether or not the store owner intends it — audit which third-party tags are present and what they can observe.]` [4f8916cd06ba] [1265]
62. **Tracking-defense arms race, presented as ongoing, not resolved (verify current state before citing any of these as fixed):** some browsers began blocking/restricting third-party cookies (Safari cited as an early strong adopter; Firefox blocked them early then reportedly rolled the restriction back at some point; Brave restricts them by default) `[web check: current default third-party-cookie policy per browser — this area changes frequently and was already described as having reversed once]`. In response, trackers moved to alternative persistence: URL-parameter-encoded identifiers, `localStorage`/other storage APIs, and a broader informal industry term "evercookie" — redundantly storing an identifier across MANY different browser storage mechanisms simultaneously so clearing any single one doesn't remove it (it "resurrects" from another copy).
63. **HSTS supercookies — a security feature repurposed as a covert, cookie-free tracking channel, described by the speaker as "the absolute grossest example" of this pattern.** HSTS (HTTP Strict Transport Security) is legitimately a security feature: a site tells the browser via a response header to never make future requests to it over plain HTTP again, forcing HTTPS even against an explicit `http://` link, protecting against downgrade/interception. Tracking abuse mechanism (described at the level needed to understand the defensive implication, not as exploit code): a tracker registers/controls an arbitrarily deep chain of nested subdomains and sets a DIFFERENT, individually-controlled HSTS instruction (present/absent) on each one, PER BROWSER — since each subdomain's "has HSTS been set for me" state persists locally as a simple, later-probeable boolean, N nested subdomains give roughly N independent one-bit storage slots; the speaker's own illustrative estimate: roughly 32 nested subdomains gives ~32 bits, enough entropy to functionally uniquely identify every browser on the planet, all without setting a single cookie. Treat the "32 subdomains -> 32 bits" figure as the speaker's own illustrative estimate, not a formal citation. `[web check: current browser-level HSTS-supercookie mitigations across Chrome/Firefox/Safari/Brave, since these evolve]` [97ced779fbd0] [3db5a465b9a7] [2046]
64. **Fingerprinting is "tracking hard mode": identifying a browser via combined weak signals rather than storing and reading back a value.** Model: each individual signal (browser family, OS, having Office installed, sending a Do-Not-Track header, using an ad blocker, etc.) narrows the matching pool of users only slightly on its own (e.g. Firefox alone is ~20% of users — hundreds of millions, not identifying), but combining enough weakly-identifying signals narrows the set down to a very small number, potentially one person, out of a global pool of roughly 3-4 billion internet users. Two properties needed for effective fingerprinting: many semi-unique signals, or a smaller number of highly unique ones (traded off against each other); an effective defense must address both fronts. [a443b97281a3] [1428]
65. **Do Not Track (DNT) is a well-meaning, failed opt-out mechanism whose adoption itself became an identifying signal.** Almost no site honored the header (the speaker: at the time, effectively only Twitter respected it in any documented way); because only a minority of users enable DNT, HAVING it set at all becomes an identifying fingerprint bit. `[web check: current DNT support/successor signals such as Global Privacy Control]`
66. **User-Agent string: sent on nearly every HTTP request and readable via `navigator.userAgent`; historically accumulated confusing legacy compatibility tokens (Chrome's UA string containing "Mozilla," "KHTML," "Safari," etc.) that combine into multiple weak identifying sub-signals.** `[web check: current browser UA-string reduction/freezing initiatives, since browsers have actively been changing this exact mechanism]`
67. **Local font enumeration is one of the hardest fingerprinting vectors to defend, because there is no direct "list installed fonts" API — it is inferred indirectly by measuring layout.** Fonts fall into three CSS categories: system (OS-default), web (explicitly downloaded per-page via CSS), and local (user-installed, e.g. from Office/Photoshop). Detection technique: render hidden text in each of a long candidate font-name list (can number in the hundreds of thousands) and measure whether the element's width/size CHANGES for that font versus a fallback — a change implies the font is installed. Hard to defend because you cannot simply block "reading element width" (breaks all layout-dependent sites) nor restrict to a tiny fixed font list without breaking real use cases, notably many Asian-language sites that depend on specific non-OS-default local fonts. Proposed (as of the talk, not yet shipped) countermeasure directions: map each page's declared LANGUAGE to a small, consistent set of allowed locally-visible fonts (trades a larger "anonymity set" for continued compatibility); require a permission prompt before non-default local-font access (does not solve the case where the USER, not the site, installed the unusual font and simply clicks through the prompt). Source of technique: a UC San Diego paper (name/author uncertain in transcript, `[web check: exact paper title/authors]`), credited (with explicit hedging) to a researcher also known for foundational return-oriented-programming work ("The Geometry of Innocent Flesh on the Bone"). [1310] [6a092ece8502]
68. **Canvas/WebGL fingerprinting exploits imperceptible, hardware-dependent rendering differences read back through a legitimate API.** The canvas API lets a page draw arbitrary graphics and read back the rendered pixel data (via data-URL/blob export), intended for legitimate uses (source's real example: detecting emoji-rendering support by drawing an emoji glyph and checking if it rendered as something other than a blank box); different GPU/driver/OS/browser combinations render identical drawing instructions with subtle, usually visually-imperceptible pixel differences (color depth, anti-aliasing, etc.), and hashing the read-back pixels yields a highly identifying per-hardware signature. WebGL fingerprinting is the 3D-rendering analog. Source's own framing: "if I put information into the system that I should already have somewhere else, I don't need to read it back out" — the READ-BACK capability, not the draw capability, is the risky part of the API surface. [1310] [86012f608d65]
69. **Cookie syncing links a fingerprint-derived identity to a cookie-derived identity, defeating simple cookie clearing as a privacy measure.** If a tracker sees a recognized cookie, it treats the user as already identified; if it sees an unrecognized cookie (e.g. after clearing), it computes a fresh fingerprint from many signals and uses that to re-link/look up the same underlying profile — described as "an extremely difficult problem to work around" from a defender's perspective. [2e4e38aa841d]
70. **Additional concrete, largely permission-free fingerprinting signal APIs named (as of the recording), called out explicitly as bad from a privacy standpoint:** CPU/hardware core count (Chromium-only, not fully standardized); Web Audio API channel count (mono/stereo/5.1); WebGL shader/instruction capability info; a non-standard but broadly Chromium-shipped "device memory" (approximate RAM) API; various network-info APIs (connection type, estimated bandwidth, hardware/network capability details). Also: device orientation/gyroscope/accelerometer readings (how the device is physically held, historically exposed without permission on many mobile browsers); Web Audio dual approach (query capabilities, or generate a waveform and measure subtle hardware-dependent output differences — an audio analog of canvas fingerprinting); WebRTC device enumeration (names/labels or unique IDs of connected mics/cameras depending on granted permission — called "pretty brutal" and hard to lie about); legacy browser plugin enumeration (an unusual/old plugin, e.g. an old Java install, is very quickly uniquely identifying if present at all). Source's overall characterization: "these are all extremely trivial [to access]... you don't need a permission" under the standard as of the talk, and calls this "bad." [1634]
71. **Screen/window height and width is probably the single most identifying AND hardest-to-defend fingerprinting signal, because it can be inferred indirectly even if the direct JS property is spoofed.** Unlike most other signals, height/width can be inferred through visible page BEHAVIOR (whether an image is fully displayed or clipped, where text wraps) even if a script cannot call the direct JS property, making it very hard to spoof consistently without visibly breaking the actual rendered layout. [406cd5055820]
72. **IP-based tracking has gotten less reliable but is not eliminated.** A named commercial vendor, MaxMind, sells IP-to-geographic-location databases; IPv6's larger address space and IPv4 exhaustion/fragmentation have both made IP-based geographic inference somewhat less consistent than before. A named related technique, "IP cookies" — tracking based on the SET of IP addresses a given browser/device has been observed using over time — is explicitly undermined by Tor or VPN use.
73. **A poorly-implemented anti-fingerprinting tool can make a user MORE identifiable than doing nothing, if it spoofs one signal without adjusting related signals consistently.** Source references (without full citation, `[web check: exact paper reference]`) research on this exact failure mode — worked hypothetical: a canvas-fingerprinting-blocking extension spoofs a signal implying an English-speaking region while a separate, unmodified `Accept-Language`-style signal still genuinely reports Spanish; the MISMATCH between the two signals is itself rare and highly identifying. Achieving full cross-system spoofing consistency is "extremely complicated" in itself.
74. **EFF's Panopticlick (in-browser fingerprint self-test, per the source about 10 years old at time of the talk) is the industry's rough benchmark for anti-fingerprinting claims.** Measures a subset of these signals and reports how many other browsers out of a reference population share the visitor's exact fingerprint (e.g. "1 in 1,000"); browsers/tools commonly cite improvement against this benchmark. `[web check: Panopticlick's current status/successor, e.g. EFF's "Cover Your Tracks" tool]`
75. **Real fingerprinting scripts typically hash each signal, then hash the combination — making a single randomized signal an effective, if fragile, countermeasure against naive implementations.** Conceptually a composite ~256-bit hash of per-signal hashes, stored/looked-up server-side; if even ONE input becomes inconsistent across visits (e.g. randomizing the User-Agent string every page load), the entire composite hash changes each time, defeating a naive fingerprinting implementation entirely ("poisoning the well in one place") — though this is not guaranteed against more sophisticated implementations that may weight/handle inconsistent signals differently.
76. **A concrete, named, widely-deployed fingerprinting library exists and is worth knowing by name for third-party-script auditing: "FingerprintJS2."** Described (at time of talk) as probably the most popular fingerprinting library online, with open-source and paid/commercial versions, "shipping on a large, large, large number of websites," and used in the source's own class exercise as broadly representative of real-world fingerprinting implementation. `[web check: current project name/maintainer/status — the open-source project has since been renamed/forked, and the commercial product rebranded; verify current names before referencing.]` [1440]
77. **Five general fingerprinting-countermeasure strategies (the speaker's own framework, with an explicit personal ranking of which are promising):** (1) Remove the functionality entirely (viable when abuse dwarfs legitimate use, per speaker's view for most of these APIs, but risks breaking sites, which is a losing strategy for a browser vendor who needs users to keep using it). (2) Force a consistent/uniform reported value across all browsers (functionally similar trade-off to removal — if every browser reports the same fake value, the real functionality is effectively gone anyway). (3) Restrict WHO can access a capability rather than changing what it reports (speaker's favored direction) — sub-approaches: permission prompts (real but limited by well-documented "permission prompt fatigue," where users habitually click "yes" without evaluating; reasonable only for the most egregious/powerful individual capabilities, not blanket coverage); "user gesture" gating (a standardized concept — click qualifies, scrolling does not — used to require genuine interaction before exposing a capability); first-party-vs-third-party restriction (grant a capability to the top-level page but deny it to embedded third-party frames/scripts); and a Google proposal loosely termed "intent engagement" using behavioral signals (visit frequency, bookmarking, home-screen add, click history) to algorithmically grant capabilities — speaker's explicit personal critique: hard to reason about predictably as a developer, and hard to explain to users what an opaque ML classifier will decide about their privacy; speaker believes Google intends to ship some version eventually but personally dislikes the approach. (4) Noise injection/steganography (speaker's favored "most promising" current direction) — make every canvas/audio/video fingerprint-relevant output SLIGHTLY, imperceptibly different (e.g. flipping low-order pixel bits) per session/site, so read-back values become unstable identifiers without visibly changing the user-facing output; Brave's concrete shipped/planned example: deliberately varying low-order sub-fields of the User-Agent string (e.g. OS patch version) frequently enough to inject noise into any hash incorporating it, without breaking coarse version-sniffing logic; explicit limitation: once a fingerprinter notices a field is being randomized, it can simply drop that field from its computation — each successfully-neutralized signal is one fewer bit available, not a permanent win. (5) Google's "Privacy Budget" proposal (Blink/Chromium team) — assign each fingerprinting-relevant API an estimated identifying-bit cost, let a page accumulate usage against a fixed budget (e.g. don't exceed roughly 1-in-1000 identifiability), impose an unspecified restriction once exhausted; speaker's STRONGLY STATED PERSONAL OPINION: "a terrible idea," "extremely unlikely to ship... in Brave, Safari, or anybody else," for three unresolved design problems he raises: what happens once budget is exhausted (does the page just break?); what is the budget's lifetime/scope (does revisiting a page reset it, letting a tracker "re-earn" bits every visit?); and whether each third party on a page gets its own separate budget (letting multiple third parties collectively fingerprint despite individual limits) or a single page-wide shared budget (letting one embedded third party exhaust the budget and break the first party's own legitimate API use, e.g. breaking an embedded maps widget). `[web check: current status of the Privacy Budget proposal / Chromium Privacy Sandbox, since this area has moved substantially since this talk — treat the entire strategy-5 discussion as historical, not current fact]` [71a101a6cbf7] [e21422b5fbbc]

### 2.9 UI denial-of-service, browser-API abuse patterns, CSRF-via-GET, history poisoning, and tab-nabbing

82. **A page can lock up an entire browser via an infinite loop, unless the browser is multi-process — know which failure mode your users' browsers are exposed to.** Historically, single-process/single-thread browsers could be permanently frozen by a page running `while(true)` (optionally with a repeating `alert()`), because the browser's own UI thread (needed to process a click on the window-close button) was blocked by the page's script — the only escape was force-quitting the whole browser process. Early mitigation: a "prevent this page from creating additional dialogs" checkbox on repeated `alert()`s, turning further calls into no-ops. Full fix: modern multi-process browser architecture runs each tab in its own process, so an infinite loop in one tab does not block the separate UI process, and the close (X) button still works by killing just the hung tab's process. Real-world legal anecdote (illustrative, not independently verified in this transcript, `[web check: exact details/outcome of this reported case before citing]`): a 13-year-old in Japan posted a trivial infinite-loop-with-`alert()` script online and was reportedly visited/arrested by police under cybersecurity/malware law, prompting significant public backlash including mass forking/re-posting of the same trivial script in protest. [f0d45c067b29]
83. **A concrete browser-API permission-tier catalog demonstrated live via an "annoying site" class demo — useful as a reference table for what a compromised or careless third-party script embedded on a storefront could do at each tier:**
   - **Level 0 (fully unrestricted, no gesture or permission needed at all):** ordinary DOM manipulation; moving/resizing browser windows via script; triggering file downloads programmatically (`<a download>` clicked via script — still Level 0 as of this recording; the instructor's OWN OPINION, explicitly flagged, is that this "should be behind a click," i.e. he considers this a plausible ongoing gap, not settled-good behavior; one real mitigation IS in place: browsers block/prompt on MULTIPLE automatic downloads in quick succession from the same page, though a single silent auto-download is still tolerated — cited legitimate use case: a "your download starts in 10 seconds" landing page); hiding the mouse cursor via CSS `cursor` property.
   - **Level 1 (requires a standardized "user gesture" — click or keypress qualifies; scrolling does not):** `window.open()` (popups; the demo could open one on almost any user interaction, track multiple open window references in an array, and move/reposition them, e.g. "bounce off screen edges"); autoplaying video WITH SOUND (muted autoplay remains permitted without a gesture); device vibration (moved from Level 0 to Level 1 specifically after advertisers abused it to vibrate devices repeatedly to grab attention — a concrete example of the permission-tier model evolving in response to observed real-world abuse, not a fixed classification); clipboard WRITE (`navigator.clipboard.writeText`-equivalent — can silently overwrite clipboard contents in direct response to any gesture, e.g. to inject unwanted promotional text/links hoping the victim pastes it somewhere and inadvertently spreads it); History API push/pop-state manipulation (can intercept the back button and re-push state to make Back nonfunctional, and can flood the history stack with duplicate entries to also defeat the "hold Back for a jump-list" escape route — legitimate, heavily-used underlying purpose named explicitly: single-page-app frameworks, e.g. React-style apps, use this same mechanism to update the visible URL without a full page reload).
   - **Permission-prompt-gated:** Geolocation, camera, microphone (as expected, and matching the earlier fingerprinting-talk coverage); once camera-class permission is granted, a "torch" API can toggle a device's camera flash/LED programmatically; custom protocol-handler registration (`navigator.registerProtocolHandler`, e.g. intercepting `bitcoin:` or `mailto:` links to route to the site's own handler) is gated behind a prompt and considered low-risk by the source even if accidentally approved; clipboard READ is explicitly gated behind a prompt (asymmetric with clipboard WRITE, principle above) specifically so a site cannot silently steal whatever sensitive content — e.g. a password — a user happens to have copied for an unrelated reason.
   - **Engagement-based (a newer, intermediate tier between a single gesture and an explicit prompt):** unmuted-autoplay-with-sound can be granted WITHOUT a fresh gesture on a specific site if the browser's own accumulated engagement tracking judges the user habitually interacts with audio/video content on that site (source's example: YouTube autoplaying with sound because of prior habitual engagement) — framed as the same general mechanism family as the earlier fingerprinting-talk's "intent engagement" ML-scoring proposal, now applied concretely to autoplay policy. `[web check: current browser autoplay policy specifics, since these have continued to evolve across Chrome/Firefox/Safari since this lecture]`
   [f0d45c067b29] [d1ee9c61779b]
   - **Non-abusive, purely beneficial API demonstrated alongside the above:** Picture-in-Picture (`requestPictureInPicture`), letting a page pop a `<video>` element into a small always-on-top floating window, no abuse angle noted.
   - **A more serious, since-patched historical bug in the cursor-hiding space (not part of the live demo, described as a past vulnerability class, not current):** a page could render a FAKE custom cursor at a deliberate pixel offset from the real (hidden) system cursor, and a since-fixed browser bug let this fake, offset cursor persist visibly even when the true cursor moved entirely outside the browser window's bounds — an attacker could calibrate the offset so that when a victim believed they were clicking a harmless element, the real (hidden, offset) cursor was actually clicking "Allow" on a live permission prompt (e.g. silently granting camera access) — a cursor-based UI-redressing/clickjacking variant. `[web check: confirm this class of cursor-spoofing bug remains fixed across current browsers before treating as historical-only]`
84. **The close-tab keyboard shortcut (Cmd+W) cannot be directly overridden by a page — but can be indirectly defeated by intercepting the keypress that precedes it, illustrating that even explicitly hardened browser shortcuts can have adjacent-API side-channel workarounds.** Browsers explicitly disallow a page from calling `preventDefault()` on Cmd+W directly (deemed "too fundamental" to let a page override). The demo site worked around this indirectly: it listens for the Cmd key alone (which necessarily precedes W in the Cmd+W chord) and, on detecting it, immediately shows a blocking modal (an `alert`-style popup or a native print-dialog trigger, chosen at random) — this modal absorbs the subsequent W keypress before it can complete the Cmd+W chord, so the tab never closes, without ever technically bypassing the "can't intercept Cmd+W directly" protection. Source's own framing: "definitely not intentional behavior... just hard to think of all these cases."
85. **`beforeunload`'s custom-warning-text abuse is fixed by design; the trigger mechanism itself remains available.** A page can register a `beforeunload` handler that, if it sets the event's return value truthy, triggers a native "leave this page?" confirmation (legitimate use cited: Gmail warning a user not to close a tab while an email is still sending). Historical abuse (now fixed): pages used to be able to supply CUSTOM warning text, and scareware sites abused this to display false threats ("leaving will give you a virus") and, on some older browsers with ambiguous button wording, to trick users into clicking the wrong button and staying trapped. Current mitigation: all modern browsers ignore any custom text a page supplies and always show their OWN fixed, unambiguous wording regardless of what the page sets — this specific deceptive-copy vector is closed by design, though triggering SOME confirmation prompt at all remains available and can still be mildly abused/annoying.
86. **A real, at-the-time-still-live CSRF-via-GET example (Google/YouTube account logout) — a worked illustration of everything covered on CSRF and SameSite in this and part 1, presented as a live, unresolved, testable claim, NOT an evergreen fact.** A specific URL existed that, when loaded, logged the visiting browser out of its Google and YouTube accounts; because the endpoint responded to a plain GET, it could be triggered purely by embedding it as an `<img>` src on ANY third-party page (the browser attempts to load any image URL regardless of origin, sending ambient session cookies along), meaning simply visiting any page containing such a hidden image silently logged the visitor out with zero interaction. Instructor's own diagnosis (explicitly uncertain, posed as an open question to investigate): "the correct thing to do here is this should be a POST request," and separately, "Google must not be using SameSite cookies" on this endpoint, since SameSite cookies would have blocked the cross-site cookie attachment regardless of GET/POST. The source also notes some similar log-out-style endpoints DID use POST but were still triggerable cross-site via an auto-submitting hidden form (`<form method="post">` plus a script that programmatically clicks its own submit button) — since plain cross-site form submission is allowed by SOP baseline, a POST-based endpoint is not automatically CSRF-safe without ALSO using SameSite cookies and/or an anti-CSRF token. `[web check: whether this specific Google/YouTube GET-based logout CSRF still exists — almost certainly long since fixed given how well-known such issues become; this was explicitly a live/testable claim at recording time, not a fact to repeat as current]` [638455ba94533]
87. **Browser-history poisoning: injecting arbitrary embarrassing/false entries into a victim's OWN browser history via a top-level popup navigation, not an iframe.** Goal: get an entry for an arbitrary (e.g. embarrassing) search query added to the victim's browser history without the victim intentionally performing that search (e.g. on a shared/family computer). Two reasons an iframe-based approach fails: some search engines refuse to be framed at all (the source's example, Bing, via the same "deny framing" header from principle 29); and even absent that, content loaded inside an iframe is NEVER added to the top-level browser's navigation history (the same reason ads in iframes never show up in a user's history). Working approach: `window.open()` a genuine TOP-LEVEL popup pointed directly at the crafted URL — a real top-level navigation IS recorded in history, unlike an iframe load. Follow-on manipulation: because the attacker retains a live cross-origin reference to the popup it opened, it can still NAVIGATE (though not read/reposition) that window on a timer, alternating it between the crafted embarrassing-search URL (recorded to history) and back to the attacker's own same-origin page (where the attacker CAN again reposition/manipulate it, since it's same-origin there), repeatedly cycling this to inject a series of different history entries while only briefly exposing each one — a direct, satisfying synthesis of the same-origin/window-reference concepts covered earlier in this part. Aside (not the core defense, included as clarification only): SameSite "Strict" cookies would prevent the target site's session cookie from being sent on such an externally-triggered top-level navigation, while "Lax" mode would still send it — but this attack doesn't care about cookies either way, since its only goal is the URL visit being recorded in history, so the SameSite distinction is irrelevant to defeating it.
88. **Tab-nabbing (`window.opener` reverse-navigation phishing) — a page opened via `target="_blank"` can silently redirect the tab that opened it to a convincing fake login page.** Setup: a trusted page (chat app, forum post/comment) links to an external, attacker-controlled site using `target="_blank"` (explicitly common and legitimate — the source notes some regional web cultures, e.g. per the source, "a lot of" sites in China, apply this broadly even to internal links, purely so users don't navigate away; Western practice more typically reserves it for genuinely external links). Vulnerability: the newly opened tab has, BY DEFAULT, a JavaScript reference back to the original tab via `window.opener`; because a script holding any window reference can NAVIGATE that window even cross-origin (though not read/modify its content — consistent with the SOP window-reference rules covered earlier), the attacker's new tab can silently set `window.opener.location` to a fake login page mimicking the original site, typically designed to look like a "you've been logged out, please log in again" state. Because this happens silently in a background tab, the victim later switches back, sees what looks like their normal login screen, and re-enters real credentials — captured by the attacker. Live demonstrated example referenced (a Reddit-posted video, watched live in class): a Reddit comment/post's `target="_blank"` link led a visitor to discover, on closing that tab, that their PREVIOUSLY-OPEN Reddit tab had silently navigated in the background to a convincing fake Reddit login page, whose URL visually resembled "reddit.com" but used a homograph/lookalike-character substitution (source: "there's an extra accent on the D") — the domain-spoofing detail is explicitly deferred, "we'll come back to that in a second," and is NOT resolved within this part. ## 3. Procedures

This part's content is almost entirely conceptual/explanatory rather than a numbered operational sequence; the source demonstrates most fixes as single-line code changes inside live demos rather than multi-step procedures. The closest things to procedures the source gives:

1. **Implementing safe `postMessage` communication (both sides required):**
   1. Sender: call `otherWindow.postMessage(data, exactTargetOrigin)` — never pass `"*"` as the origin.
   2. Receiver: register `window.addEventListener('message', handler)`.
   3. Inside the handler, FIRST check `event.origin` against the exact expected origin (or an explicit allow-list) — reject/return if it does not match — THEN use `event.data`. [796]

2. **Fixing reflected XSS in a server-rendered template (the source's live "bank site" welcome-banner demo):**
   1. Identify every place an untrusted, request-derived value (query parameter, header, etc.) is concatenated into a server-rendered HTML response.
   2. Apply HTML-entity escaping to that value ONLY, at the exact point of insertion — not to the surrounding developer-authored markup, not to the whole page. [1219]
   3. If using a framework, use its templating layer's default (auto-escaping) interpolation syntax rather than an unescaped/raw-output syntax, unless the value is provably not attacker-influenced.
   4. Re-test every code path/branch where the vulnerable output can render (the source's own demo initially missed the logged-in-user branch because the vulnerable banner logic only ran for logged-out visitors, requiring a manually-set test cookie to confirm the cookie-theft payload worked once actually logged in) — test all states, not just the first one found.

3. **Choosing an escaping/handling technique by HTML context (decision sequence, synthesized from principles 44-54):**
   1. Is the untrusted value going into plain tag text content? Escape `&` and `<` only. [1ffc9074018e]
   2. Is it going into a QUOTED attribute value? Escape both quote characters (always, regardless of which quote type the template uses). [6ee053ebfcc9]
   3. Is the attribute unquoted? Stop — add quotes first; do not attempt to enumerate the lax-parser's delimiter character set. [1099]
   4. Is the attribute `src`/`href` or another URL-accepting/"powerful" attribute? Quote-escaping is not sufficient — additionally validate the value is well-formed and restricted to an expected scheme allow-list (e.g. `http`/`https`), rejecting `data:`/`javascript:` and anything else unexpected. [95fe4dae87431]
   5. Is the value going inside an inline `<script>` block's JS string, or an inline event-handler attribute's embedded JS? Do not rely on quote/backslash escaping alone (it cannot neutralize an embedded `</script>` breakout, and event-handler contexts nest HTML-attribute and JS-string escaping simultaneously). Prefer hex-encoding the value and decoding it at runtime, OR move it into a `<template>` tag and retrieve it via `document.getElementById(...).content` at runtime instead. [c9669d9997786] [48e61c95a937]
   6. Is the destination context an HTML comment, a tag name, or an attribute name? Do not place untrusted data there under any escaping scheme — restructure the feature so user input never determines these. [1ffc9074018e]
   7. Does the value cross MULTIPLE nested contexts (e.g. JS string inside a function call inside an HTML attribute)? Restructure the code to avoid the nesting; if unavoidable, re-apply the correct escaping for each context in the correct order and verify by hand, since no single escaping pass covers more than one context boundary.

4. **Hardening a page against being framed (clickjacking defense):** set the response header that denies framing entirely, or restricts it to same-origin, on every response for pages that should never be embedded (e.g. checkout, account, admin) `[verify UI: exact header/value per current standard — X-Frame-Options `DENY`/`SAMEORIGIN` or CSP `frame-ancestors`, and confirm current browser support]`. [c3411ca931e1]

## 5. Diagnostics and checks

- **`postMessage` audit:** for every `postMessage` call in your codebase, confirm the second argument is an exact origin string, never `"*"`; for every `message` event listener, confirm `event.origin` is checked against an exact expected value (or allow-list) before `event.data` is used. Bad: any listener that reads `event.data` before an origin check, or that has no origin check at all. [35429981841411264488edb3]
- **Third-party script audit:** list every `<script src>`, `<link>`, `<iframe>`, and pixel/tag embedded on storefront pages (checkout and account pages especially); for each, confirm you know who controls that origin and what it can therefore do with the including page's full privileges (read cookies via JS if not HttpOnly, manipulate the DOM, make authenticated requests). Bad: any script from an origin the store owner cannot name or does not actively monitor. [0cc21dc1fdd0]
- **Cookie-attribute check on every session/auth cookie:** confirm `SameSite` is set (and appropriate mode chosen per Lax/Strict trade-offs from part 1); confirm `Path` is not relied on as a security boundary for anything sensitive. Bad: a session cookie with no SameSite attribute set at all, especially on any endpoint reachable via GET that changes state (login/logout/cart/settings). [f4015dad3b23] [d721b7f8d72e]
- **Framing check:** load each sensitive page (checkout, account settings, admin) inside a test iframe from a different origin and confirm it is refused/blank. Bad: the page renders normally inside the cross-origin iframe. [c3411ca931e1]
- **GET-request state-change audit (directly modeled on the live Google/YouTube CSRF example):** grep server routes for any GET (or image-triggerable) endpoint that changes account/session state (logout, cart-clear, settings toggle) without a CSRF token or SameSite-cookie protection. Bad: any such endpoint reachable by simply loading an `<img src="...">` pointed at it from another site. [638455ba94533]
- **Reflected/stored XSS spot-check:** for any field that accepts free text and is later rendered back to the SAME or ANY OTHER user (search box, review, profile name, wishlist name, seller bio), submit the harmless test payload pattern `<script>alert(document.cookie)</script>` (and its HTML-entity-encoded and hex-encoded variants) and confirm it renders as inert visible text, not as an executed script or altered DOM structure. Bad: the alert fires, or the payload disappears/executes silently. [2df9b830a02e] [0393d1e220fb]
- **Tab-nabbing audit:** grep templates/components for `target="_blank"` without an accompanying `rel="noopener"` (and ideally `rel="noreferrer"`) on any link to an external/uncontrolled origin. Bad: any outbound `target="_blank"` link with no `rel` attribute at all. [d749fee9fe72]
- **Third-party-tag privacy audit (for compliance and for spotting unexpected data flows), per the guest lecture's framing:** list every third-party tag/pixel on the storefront and identify, for each, whether it sets or reads a cookie, what data it can observe about the visitor, and whether its use has been disclosed/consented to for that specific purpose (relevant to the purpose-limitation legal principle in 2.8). Bad: a tag whose vendor, purpose, or data flow the store owner cannot describe. `[needs brand data: full list of third-party scripts/tags actually embedded on the storefront]`

## 8. Mistakes the source warns about

- Relying on `document.domain` relaxation anywhere in a codebase — treat any occurrence as a red flag to investigate, not a pattern to use. [784]
- Calling `postMessage` with `"*"` as the target origin, or omitting the `event.origin` check in a `message` listener — either mistake alone reopens the exact leak/spoof scenarios in principles 4-5. [796]
- Relying on the Referer header (or a site's willingness to send it) for any access-control decision — both browser caching and `Referrer-Policy` can silently defeat it. [332f8d82f1e1]
- Treating cookie `Path` scoping as a security boundary — it is not; any same-origin script/frame can still read the full-origin cookie. [d721b7f8d72e] [4388ab8bc2f2]
- Using client-side frame-busting JavaScript instead of the server-side anti-framing header — frame-busting has been comprehensively shown to be bypassable.
- Assuming an anti-framing check only needs to verify the immediate parent frame — must check the full ancestor chain, per the MySpace/ad framing-chain bug.
- Using JSONP to pull data from any third party into a store's own page — grants that third party (or anyone who compromises it) full script execution on the store's page. [4b7cd675a290]
- Denylisting/pattern-matching specific strings (`<script>`, `onload=`, etc.) as an XSS defense instead of output-escaping — the HTML parser's own leniency reliably defeats denylists. [825a61a6a5f9]
- Escaping only quote characters when the template uses unquoted HTML attributes — quoting escapes protect nothing if there are no quotes to break out of; always quote attributes instead. [1099]
- Treating quote-escaping as sufficient for `src`/`href`/other URL-accepting attributes — scheme/well-formedness validation is a separate, required control. [95fe4dae87431]
- Placing untrusted data inside an inline `<script>` block and escaping only quotes/backslashes — a literal `</script>` in the data still breaks out at the HTML-parsing layer regardless of JS-level escaping; use hex-encoding or the `<template>` tag instead. [c9669d9997786]
- Letting user input determine an element's `id`, an attribute name, or a tag name — each opens a distinct, hard-to-escape-around vulnerability class (global-variable clobbering, and unpredictable parser/denylist interactions respectively).
- Putting user data inside an HTML comment — the parser rules for safely escaping this are unusually hard to get right, and there's no legitimate reason to do it.
- Writing deeply nested code where a value must be escaped for three or more contexts in sequence (JS string inside a function call inside an HTML attribute, etc.) — the source calls this "surprisingly common" and easy to get subtly wrong; avoid the pattern entirely rather than trying to get the nested escaping exactly right.
- Assuming a `<script src>`-loaded third-party library only affects "its own" functionality — it runs with the FULL privileges of the including page's origin; a compromise of the third party is a compromise of the including page.
- Assuming a POST-based state-changing endpoint is automatically CSRF-safe — it is not, unless it also uses SameSite cookies and/or an anti-CSRF token, since cross-site auto-submitting forms are allowed by SOP baseline.
- Adding `target="_blank"` to an outbound link without `rel="noopener"` — leaves the linking page open to being silently redirected by the newly-opened tab via `window.opener` (tab-nabbing). [d749fee9fe72]
- (Guest lecture) Deploying a fingerprinting-blocking or privacy tool that spoofs one signal without keeping all related signals consistent — can make a user MORE identifiable than doing nothing.
- (Guest lecture) Assuming DNT, third-party-cookie blocking status, or ad-blocker use are themselves privacy-neutral — each, being a minority behavior, is itself a fingerprinting-relevant signal.
