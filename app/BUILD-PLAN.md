Date: 25 Sep 2026. Status: Phase A done 26 Sep 2026 (server, kit, generator, metric contract, Today round 0 pending). Update 28 Sep 2026: the product is general purpose for any e-commerce store, and the sample brand becomes Bombas (public profile, simulated data). ## The idea in one paragraph

The Meta gallery worked because it started as one page on real data and grew a feature at a time, each one asked for, built, looked at, and kept or dropped. We do the same for every part of the business. Each screen gets its own folder and its own build sessions. A sample US brand with generated data stands in for a real client so every screen can be built and judged now. When a real brand connects, the same tables fill from connectors and the screens do not change. The agent layer comes after the screens, because the screens tell us exactly which jobs need an agent and which need a connector.

## The sample brand

Name: **Tallgrass Goods** (fictional). A US direct-to-consumer brand selling kitchen and home goods: cast iron, linen, wooden boards, about 40 SKUs, average order around $85, Shopify, ships from a 3PL in Ohio, paid social led, email second, Amazon as a secondary channel, no subscriptions. Not a real company. Every page says so. Its facts live in `app/data/sample-brand/brand.json`; its tables are generated by `app/data/generate.py` from a seed so the numbers are stable across sessions and shaped like real connector output.

The sample brand has every connector. Kevin decided on 25 Sep 2026 to generate every table in `contracts/data-sources.md`, including support tickets, Klaviyo flows, reviews, payouts and speed runs, so each screen shows its full function in a demo. "Unavailable" then only appears for a real brand that has not connected a source.

Subscription brands need different metrics (payback period, churn, cohort revenue curves). They come later as a second sample brand with its own generator profile, not as a fork of the screens.

## Feature rounds

A round is: the founder opens a screen session and asks for 10 candidates. The session builds the list from 3 sources and ranks it.

1. `FEATURES.md` in the screen folder, seeded from the room spec: the questions a founder asks, the metrics with formulas, the insights as rules, the visuals, the not-elsewhere claims, the data needed.
2. The capability catalogue for the screen's agent, and its workflows and skills, by id.
3. One web pass on what the common tools in that domain show today, so we know what is table stakes and what is new.

Ranking, in this order: revenue impact for a brand like the sample, usefulness to a founder deciding alone in under a minute, buildable now on dummy data (a feature that needs a connector we do not have is parked with the connector named). The founder picks. Each picked feature is one commit with `FEATURES.md` updated. When a round lands, the screen is published as a page and the round is logged.

## Where agents and connectors come in

The screens are built as if the data were there. Two things fill them later:

- **Connectors** (read-only adapters in `app/connectors/`, each with a mock mode that returns the generated tables): Shopify, GA4, Meta Ads, Google Ads, Klaviyo, Gorgias, Search Console, Amazon Seller, Reddit and review sites for research, page speed. The generator's tables are shaped like each connector's output, so switching from mock to live is a config change per brand.
- **Agents** (the catalogue in `agents/`): each action button on a screen already names its capability. When the agent layer is built, the button dispatches the workflow instead of logging a stub. The screens tell us the order to build agents in: the buttons founders press most.

Anything that needs an external API we do not have yet (Reddit, Amazon reviews, TikTok) is built against a fixture file in the screen's `fixtures/` folder, with the connector interface written and the live call left as a TODO with the endpoint named.

## How to run this in Claude Code

**Sessions.** One session per screen folder, started with the folder as the working focus. Say the folder and the round. Example first line: "Work in app/screens/07-landing-pages-cro. Round 1. Give me 10 candidates." The session reads `app/CLAUDE.md`, `app/contracts/`, and the folder. That is about 6 to 10k tokens of context, not 300k.

**Models.** Planning a round and ranking candidates: Fable (judgement, reads the spec, argues the ranking). Building a picked feature: Opus, or Sonnet for a small one. Contract changes and the round-0 kit: Fable, because everything depends on them. A separate short Fable session reviews a screen's round for consistency with the contracts before it is published.

**Parallel work.** Screens in different phases can run in separate sessions at the same time, in separate worktrees, because they share only `contracts/` and `data/`. Two sessions must not edit `contracts/` at once; contract changes are their own small session, committed first.

**Token rules.** Reference files with `@path`, never paste them. `/clear` between features. Ask for 10 candidates, pick, then build one at a time. Do not ask a build session to "improve the screen"; ask for the one feature by number. Commit after every feature so a lost session costs one feature, not a round. Compaction should be rare because sessions are short by design.

**Memory across sessions.** Three files carry it: `app/CLAUDE.md` (contract), `screens/<x>/FEATURES.md` (what is done, what is next, why something was parked), and git history. A session that needs to know why a decision was made reads the commit message, not a transcript.

**Publishing.** After a round lands, the screen is published as a page (the way the gallery and the speed plan are), so it can be looked at on a phone and shared. The local server stays the working copy.

## Round 0 checklist (phase A)

1. `app/server.py`: static files, `/api/<screen>/...` routed to each screen's `api.py`, `/api/brand`, `/api/metrics/<name>` from the contract, decisions log write.
2. `app/web/`: nav shell listing screens from `screens/INDEX.md`, `ui-kit.css`, `ui-kit.js` (tiles, insight cards, decision row, tables, founder note), `charts.js` (bar, line, step, funnel, cohort grid), filmstrip player ported from the speed lab.
3. `app/data/generate.py`: from `brand.json`, generate 13 months of orders, customers, sessions, ad rows at ad level, email flows and campaigns, tickets, reviews, products with costs, inventory, speed runs, marketplace listings. Deterministic seed. Shaped like each connector's export.
4. `app/contracts/metrics.md`: the starter metric contract for a normal DTC brand, formulas and sources, with the reversed-orders group.
5. `00-today`: the pipeline with the break marked, computed from the generated data; the top 10 as stubs reading from the room spec; the decision row writing to `decisions.json`.

## What we do not do

- No agent execution yet. Buttons log decisions. The catalogue stays the spec.
- No real brand data in `app/`. Gehna stays in `meta_gallery/` and `data/meta-gallery/` until a connector migration is decided.
- No India-specific defaults. Market fields exist and read null.
- No feature without a formula, a rule or a capability id behind it.
